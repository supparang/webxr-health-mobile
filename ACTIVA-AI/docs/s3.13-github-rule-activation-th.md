# ACTIVA-AI S3.13 — คู่มือปิดข้อบกพร่อง P0 การป้องกัน GitHub

**สถานะ ณ 15 ตุลาคม 2569:** ร่างสำหรับผู้ดูแลระบบเท่านั้น ยังไม่เปลี่ยน Ruleset จริง ไม่ Merge และไม่ Deploy ระบบ Production ยังคง **HOLD / NO-GO** การอนุมัติจริยธรรมวิจัยเป็นอีกกระบวนการหนึ่ง

## 1. หลักฐานที่ยืนยันได้

- GitHub แสดงสาขา `main` ว่า `protected: false` (commit `c89adc1712dd02650b2ad41dc4bbdd7f3b6c0100`)
- Ruleset `herohealth` หมายเลข 14531785 แม้มีสถานะ active แต่ไม่มีค่ารายชื่อสาขาใน `ref_name.include` และไม่มีข้อกำหนดให้อนุมัติโดยบุคคล 2 รายหรือผ่าน CI
- ไม่พบ CODEOWNERS ที่ตำแหน่งมาตรฐานทั้งสามแห่งบน main
- ระบบเชื่อมต่อ GitHub เข้าถึง classic branch protection API ได้ผล 403 เพราะสิทธิ์ของ Integration **จึงห้ามแปลว่าไม่มีกฎอยู่เลย**
- CI ของ S3.12 PR #164 ผ่านแล้ว แต่เป็นการทดสอบซอฟต์แวร์ ยังไม่มีหลักฐานการตรวจรับจากฝ่าย Security/Operations

งานคงค้างเปิดไว้ที่ https://github.com/supparang/webxr-health-mobile/issues/163

## 2. สิ่งที่จัดทำใน S3.13

ไฟล์ `security/s3.13-main-ruleset.CANDIDATE.json` เป็น **กฎเสนอสำหรับนำเข้า** โดยตั้ง `enforcement: disabled` อย่างตั้งใจ เพื่อไม่ให้ผู้ดำเนินงานนำกฎไปใช้ก่อนจัดเตรียมผู้ตรวจทานจริง กฎระบุ `~DEFAULT_BRANCH` และ `refs/heads/release/*` บังคับ PR + ผู้อนุมัติอย่างน้อยสองราย ตรวจ code owner ตรวจ approval หลังมี push ใหม่และ dismiss stale approvals ตรวจ unresolved conversations กำหนดสถานะ CI `smoke` แบบ strict และป้องกัน force push / deletion กฎนี้ไม่มีรายชื่อผู้ยกเว้น (`bypass_actors: []`)

Workflow `.github/workflows/activa-ai-ci.yml` ถูกปรับให้รันสำหรับ PR **ทุกคำขอ** (เดิมมี path filter) เพื่อหลีกเลี่ยงเหตุการณ์ที่ GitHub รอ Required Check ชื่อ `smoke` ซึ่งไม่เคยเริ่มทำงานใน PR ที่ไม่ได้แก้โฟลเดอร์ ACTIVA-AI ผลคือ CI หนักจะทำงานมากขึ้นใน Repository หลายโครงการ ผู้ดูแลต้องยืนยันต้นทุน/ระยะเวลาของ CI และอาจออกแบบ workflow แยกในอนาคตโดยไม่ลดมาตรฐานการป้องกัน

**ยังไม่ได้สร้าง CODEOWNERS จริง** เนื่องจากต้องทราบ GitHub account ที่มีอยู่จริงและมีอำนาจหน้าที่ตามที่หน่วยงานอนุมัติ การใส่ตัวอย่างชื่อปลอมเข้าไปใน CODEOWNERS ไม่ได้สร้างผู้ตรวจทานอิสระ

## 3. ขั้นตอนที่ผู้ดูแล GitHub ต้องดำเนินการจริง

1. มอบหมายบุคคลหรือหน่วยงานที่มีอำนาจอย่างน้อยสองฝ่าย (Security กับ Operations) และยืนยัน **บัญชี GitHub จริง** ที่มีสิทธิ์ review repo พร้อมบันทึกหลักฐานในระบบเอกสารที่จำกัดสิทธิ์ การเป็นเจ้าของ Repository เพียงคนเดียวไม่ถือเป็นการตรวจสอบโดยอิสระ
2. จัดทำ `.github/CODEOWNERS` ใน PR ที่มีการทบทวนโดยผู้มีอำนาจ และกำหนดเจ้าของไฟล์ด้านความปลอดภัย เช่น `.github/CODEOWNERS`, `.github/workflows/*`, `/ACTIVA-AI/server/release-authority-trust.js`, `/ACTIVA-AI/server/production-release-approval.js`, `/ACTIVA-AI/server/deployment-config.js` และไฟล์ที่เกี่ยวข้องกับการเผยแพร่ระบบ โปรดทราบว่า CODEOWNERS หลายชื่อบนบรรทัดเดียวไม่ได้บังคับให้แต่ละคนต้องอนุมัติทุกคน จึงต้องใช้ข้อกำหนดสองอนุมัติร่วมด้วย และตรวจความเป็นอิสระของผู้อนุมัติจริง
3. ใน GitHub ไปที่ **Repository → Settings → Rules → Rulesets → New ruleset → Import a ruleset** แล้วเลือกไฟล์ `s3.13-main-ruleset.CANDIDATE.json`; ตรวจสอบทุกฟิลด์ในหน้า GitHub ก่อนบันทึก ถ้า UI นำเข้า JSON รูปแบบนี้ไม่ได้ ให้สร้าง **New branch ruleset** ด้วยค่าตามข้อ 2 แทน ห้ามถือว่าการ import สำเร็จจนกว่าจะดูผลใน Settings และอ่านกฎย้อนหลังจาก API
4. ก่อนเปิด `Active` ให้ตรวจว่ารายชื่อผู้ตรวจทานจริงใช้งานได้ `CODEOWNERS` อยู่ใน default branch, check `smoke` มีจริงใน PR ทุกประเภท (รวมไฟล์นอก ACTIVA-AI), branch selector ครอบคลุม `main` และ `release/*`, และไม่มีคนใดสามารถข้ามการอนุมัติทั้งหมดเพียงคนเดียว
5. ผู้ดูแลที่ได้รับอนุญาตจึงเปิด `Active` และร่วมกับ Security ตรวจซ้ำใน GitHub UI/REST **กฎที่มีผลจริง** โดยไม่แก้/ลบ ruleset ของ `herohealth` ซึ่งใช้กับงานอื่นโดยไม่มีการประเมินผลกระทบ
6. ทดลอง PR ที่มีไฟล์โค้ดความปลอดภัยและอีก PR ที่มีเฉพาะไฟล์เอกสาร เพื่อพิสูจน์ว่าไม่มีวิธี Merge โดยไม่มีสองอนุมัติหรือข้าม CI และไม่มี deadlock เพราะ check ไม่ปรากฏ **ห้ามทดสอบโดย Merge เข้า main โดยไม่ได้รับอนุญาต**
7. เก็บหลักฐานหน้ากฎที่ตั้งค่าจริง ผู้มีอำนาจสองราย การทำงานของ CODEOWNERS, บันทึก CI ที่ exact SHA และการตรวจสอบ bypass list โดยผู้ตรวจอีกฝ่ายไว้ในระบบเอกสารที่จำกัดสิทธิ์ จากนั้นจึงพิจารณาปิด Issue #163

GitHub Documentation: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository

## 4. เกณฑ์ผ่าน

- main และ release branches อยู่ภายใต้กฎ active ที่มีผลจริง
- มีผู้ตรวจมนุษย์อย่างน้อยสองฝ่ายตามอำนาจหน้าที่ และ CODEOWNERS ได้รับการบังคับใช้กับไฟล์สำคัญ
- Required CI ทำงานและถูกบังคับก่อน Merge โดยไม่มีช่องทาง bypass ไม่ได้รับอนุญาต
- มีหลักฐานจากผู้ดูแลและผู้ตรวจอิสระว่าทดลองทั้ง positive/negative cases ได้ตามผล
- ยังต้องผ่าน Staging ที่แยกจริง, ภาคสนาม 25 กรณี, SIEM จริง และ signoff แยกต่างหากก่อน Production GO

**ผลตรวจ CI ของ Candidate ไม่เท่ากับการอนุมัติ Production หรือรับรอง Repository**
