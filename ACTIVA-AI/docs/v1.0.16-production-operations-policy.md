# ACTIVA-AI V1.0.16 — Production Operations Policy

**Status:** Phase 2 baseline approved for implementation  
**Scope:** Operational controls for the accepted `ACTIVA-AI-1.0.15` production baseline while V1.0.16 Phase 2 is being closed.

## 1. Alert ownership and escalation

GitHub Production Monitor is the primary operational alert channel for Phase 2.

- Primary owner: `supparang`.
- A failed monitor run opens or updates one GitHub incident.
- Repeated failures append to the existing incident.
- Recovery closes the incident automatically after a successful monitor run.
- The alert contains no participant-level data or credentials.
- A secondary alert destination is optional and is not a Phase 2 blocking condition while GitHub alert routing remains verified and operational.

Escalate immediately when:
- `/api/ready` fails;
- database connectivity is unavailable;
- authentication readiness fails;
- deployment tier is not `PRODUCTION`;
- release identity differs from the accepted release;
- `autonomousDecision` is not `false`.

Operational alerts never replace Human GO/HOLD or participant-level review decisions.

## 2. Log retention and redaction baseline

ACTIVA-AI application access logs are operational telemetry only.

Required fields:
- request ID;
- UTC timestamp;
- HTTP method;
- path;
- response status;
- duration;
- deployment tier.

Prohibited in access logs:
- request/response bodies;
- email addresses;
- employee IDs;
- OAuth tokens;
- QR secrets or credentials;
- database credentials;
- participant-level evidence payloads.

Phase 2 retention baseline:
- ordinary application/access logs: retain no longer than 30 days unless an approved incident investigation requires longer preservation;
- GitHub recovery evidence artifacts: 30 days;
- immutable ACTIVA-AI audit records remain governed by the application data-retention policy and are not treated as disposable provider logs.

Any provider configuration that captures request bodies must be disabled or redacted before real-activity rollout.

## 3. Production user provisioning and deprovisioning

Production users are provisioned explicitly. Google sign-in never creates roles automatically.

Provisioning:
1. Confirm approved identity and organizational role.
2. Create or activate the ACTIVA-AI user with the minimum required base role.
3. Add activity permissions only where needed.
4. Add per-activity assignments separately.
5. Verify the account through the production login path.
6. Record the administrative action in the Audit Trail.

Deprovisioning:
1. Set the account to inactive before removing any historical reference.
2. Revoke active per-activity assignments where operationally appropriate.
3. Do not rewrite historical Audit Trail or immutable activity evidence.
4. Review whether associated secrets/credentials require rotation.
5. Confirm the user can no longer authenticate into an ACTIVE role.

No administrative role may be granted solely from job title.

## 4. Secret rotation procedure

Secrets are rotated independently by purpose:
- `QR_SIGNING_SECRET`;
- `RESEARCH_HASH_SALT`;
- Google OAuth client secret where applicable;
- production database credentials;
- any provider deployment token used by operations.

Routine baseline: review rotation need at least every 90 days and rotate immediately after suspected disclosure, personnel access change, provider incident, or unauthorized exposure.

Rotation sequence:
1. Place rollout under operational HOLD for the affected secret.
2. Record the current release/health state.
3. Create the replacement secret in the provider secret store.
4. Update only the intended production environment.
5. Redeploy/restart through the reviewed deployment path.
6. Verify `/api/live`, `/api/ready`, and `/api/health`.
7. Verify sign-in and one non-destructive operational path relevant to the rotated secret.
8. Revoke the old credential after the replacement is confirmed.
9. Record the rotation event without storing the secret value.
10. Run Production Monitor and close HOLD only after verification passes.

`RESEARCH_HASH_SALT` must not be casually rotated if doing so would break approved pseudonymization continuity. Such a change requires a documented data-governance decision.

## 5. Dependency and runtime patch cadence

Automated dependency review is enabled through Dependabot for:
- npm dependencies under `/ACTIVA-AI`;
- GitHub Actions under `/.github/workflows`.

Cadence:
- automated update review: monthly;
- urgent security advisory: assess as soon as surfaced;
- production deployment of updates: only after CI and relevant acceptance checks pass.

Major-version upgrades are not auto-merged. Runtime/Prisma/Node changes that can affect database behavior require staging verification before production rollout.

## 6. Custom domain and secondary alert channel

These are optional Phase 2 extensions, not blockers, while:
- the production API remains HTTPS;
- exact CORS/origin controls remain correct;
- Google OIDC production readiness passes;
- GitHub alert routing remains verified.

If a custom domain is adopted later, repeat TLS, CORS, OAuth-origin and production-monitor verification before use.

## 7. Phase 2 closure rule

Repository-side operational governance is considered implemented when:
- this policy is version controlled;
- Dependabot configuration is present;
- Production Monitor alert routing has a verified fail/recover cycle;
- Neon isolated recovery workflow is present on `main`.

Full Phase 2 closure still requires:
1. one successful guarded Neon PITR isolated restore drill with retained evidence;
2. a successful normal Production Monitor run after cleanup;
3. one controlled First Real Activity acceptance with immutable closure and audit evidence.

Human Final Decision remains authoritative throughout.
