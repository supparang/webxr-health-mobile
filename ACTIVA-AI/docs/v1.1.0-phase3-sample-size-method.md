# ACTIVA-AI Phase 3 — Sample Size Planning Method

**Protocol:** `ACTIVA-P3-RP-001`  
**Sample-plan ID:** `ACTIVA-P3-SP-001`

## Method

For the binary target `REVIEW_REQUIRED`, Phase 3 uses the Riley et al. prediction-model development criteria through the maintained Python implementation `pmsampsize 0.1.0`.

The development minimum is the largest sample size required to address:

1. global shrinkage target ≥ 0.90;
2. small optimism in explained variation;
3. precision of the overall outcome risk.

A fixed “10 events per variable” rule is not used as the primary planning method.

## Required ACTIVA assumptions before calculation

The plan must specify **before empirical final-test inspection**:

- anticipated prevalence of `REVIEW_REQUIRED` and its source;
- number of candidate predictor parameters, counting dummy parameters rather than raw feature names;
- anticipated model strength as one of Cox–Snell R², Nagelkerke R², or C-statistic, with source;
- target shrinkage;
- final internal test holdout fraction.

ACTIVA's frozen baseline has 12 numeric/binary predictors plus `activity_type`. If `activity_type` has K pre-specified levels, it contributes K−1 dummy parameters.

## Why the total collection target is larger than the Riley development minimum

The existing ACTIVA baseline pipeline reserves an internal final-test holdout. Therefore, the Riley development minimum must remain available in the development portion.

With a 20% final-test holdout:

`N_total = ceil(N_development / 0.80)`

This is an engineering/research-design inflation for the existing pipeline. It is **not** claimed to be an external-validation sample-size calculation.

## High-discrimination safeguard

Recent simulation evidence indicates formula-based development sample sizes may be optimistic when anticipated discrimination is high. Therefore, if the planning assumption uses C-statistic ≥ 0.80, ACTIVA marks a simulation stress test as required before sample-plan approval.

## Clustering

`pmsampsize` does not establish a minimum number of unique participants or activities for ACTIVA's clustered data structure. Those minima must be justified separately based on the intended group-aware splitting and operational diversity. The planner deliberately leaves them unresolved rather than inventing values.

## Planning-cohort snapshot

ACTIVA provides an ADMIN-only aggregate endpoint:

`GET /api/ml/planning-summary?lockedBefore=<ISO-8601 UTC>`

It returns only aggregate counts: LOCKED records, target counts, prevalence, unique participants, unique activities, and activity-type levels. It does not return participant identifiers.

Once a planning snapshot is used to source prevalence or activity-type levels, its cutoff must be recorded in the sample plan. Records at or before that cutoff are **development-only** and may not later enter the final test set. This prevents the final test labels from influencing sample-size planning.

## Command

```bash
python ml/plan_phase3_sample.py \

  --output ml/phase3-sample-plan-result.json
```

A HOLD result is expected while required assumptions are missing.
