# ACTIVA-AI S3.6 — Operator-Gated Staging & SIEM Security Acceptance

**Status on 15 October 2026: HOLD — no verified isolated institutional
Staging, independent SIEM receiver, or manual acceptance.**
This is an operator runbook and offline evidence inventory, not an
authorization to merge, deploy Production or collect real research data.

## 1. Why this stage exists

Source PRs #136–#155 cover S2.1–S3.5 and remain in the review chain.
Local/database/Chromium CI has verified code pathways and simulated
incidents. **It has not shown that the institution operates dedicated,
isolated Staging infrastructure or actually receives/acknowledges SIEM
alerts.** Repeating mock CI cannot close that gap.

S3.6 adds an offline read-only inventory and an explicit work order for
Security/Operations, with one manifest listing infrastructure references
and **25 manual checks** (S2.10 M01–M13 and S3.5 S35-M01–S35-M12).
All default to `NOT_TESTED`.

## 2. Infrastructure the institution must provide

| Service/control | Responsible party | Required evidence |
| --- | --- | --- |
| Separate backend and frontend Staging origins with exact deployed commit | Deployment/Infrastructure | Approved HTTPS host ownership, deployment SHA, environment restrictions and `GO=false` |
| Isolated test PostgreSQL and migration credentials | Database administrator | Unique provider/database identity distinct from Production, test-only data, DB TLS certificate/hostname checks, least privileges and restore test |
| Separate key custody | Secrets/Operations | Secret manager permissions/rotation for QR, OIDC, HMAC SIEM, database and signing keys; never in PR or CI logs |
| Operator-owned **Staging-only** SIEM receiver | Security Operations | Independent reviewed HTTPS host, outbound egress allowlist, request HMAC verification, HMAC-signed receipts, durable idempotent ingestion and retention |
| Network protection | Infrastructure/AppSec | WAF/DDoS, trusted proxy hop chain, forwarded-header spoof tests and >200 synthetic concurrent clients over realistic shared-IP routes |
| Alert team | Primary and backup on-call responders | Real controlled incident, receipt, acknowledgment, fallback, escalation and runbook record |
| Independent technical reviewers | AppSec, Privacy/DPO and Operations | Repository review of cumulative diffs, privacy rules, Critical/High closure and approved change process |

Never aim S2.10 or S3.5 tests at the known Production host to fill in
missing Staging evidence. Do not use actual participant details, personnel
accounts or campus logs unless independently permitted.

## 3. Prepare and run the offline inventory (no network)

```bash
cd ACTIVA-AI
cp security/s3.6-staging-readiness.template.json /secure/activa-staging-readiness.json
node scripts/assess-staging-readiness.mjs --input security/s3.6-staging-readiness.template.json
```

The checked-in template MUST remain truthful `NOT_TESTED` and `HOLD`.
The optional **operator copy** should live in the institution's restricted
record store (not an open GitHub issue or repository). In that operator copy:

1. Supply the exact 40-hex proposed deployed candidate SHA and its
   separately verified Staging deployed SHA.
2. Record **only** exact, preapproved HTTPS Staging API, frontend and
   separate sandbox SIEM origins. Do not put credentials in URLs.
3. Add **SHA-256 fingerprints of independently reviewed database instance
   identity strings**, not raw credentials/connection URLs. The Staging
   and Production database identities must differ. These fingerprints are
   self-declared hints until the database administrator independently
   verifies source material in restricted records.
4. Set `syntheticDataOnly=true` and `productionGoDisabled=true` only
   after authorized staff have observed the actual test environment.
5. Attach **opaque ticket references** such as `OPS-STAGING-REVIEW-0001`
   or `SEC-APPSEC-REVIEW-0001`; do not attach screenshots, identities,
   tokens, session logs or GitHub URLs in the JSON.
6. For each S2.10 manual `M01`–`M13` and S3.5 `S35-M01`–`S35-M12`,
   set `status: "EVIDENCE_RECORDED"` with a corresponding valid restricted
   ticket only after the actual test. `EVIDENCE_RECORDED` is **not PASS**.
7. Submit the restricted tickets, GitHub Actions checks, SIEM receipts and
   exact deployed SHA to *separate* Security and Operations reviewers;
   they must verify each artifact's authenticity, scope, timestamps,
   signer identity and independence.

The validator accepts only the exact schema and opaque evidence IDs. It
rejects missing evidence, Production-like test destinations, non-HTTPS
or mismatched Staging origins, same Staging/Production database identity
fingerprints, `GO` enabled, no synthetic-data guarantee and mismatched
deployed source SHA. It never prints secret values or raw ticket content.

### Important outcome distinction

| Validator output | Actual meaning |
| --- | --- |
| `MISSING_DECLARED_EVIDENCE` | Some required evidence fields or manual test records are absent |
| `READY_FOR_INDEPENDENT_PROVENANCE_REVIEW` | Fields have been supplied, but **their truth and authenticity have not been independently checked** |
| `decision: HOLD` | Always returned; no approval, merge or deployment can be generated by this tool |
| `claimsVerified: false` | The program cannot authenticate an institutional ticket just by reading a JSON reference |
| `manualAcceptanceVerified: false` | Recording 25 references is not completing an independent security acceptance |

The file generated at `test-results/s3-6-staging-readiness.json` in CI
contains only coarse check IDs/owner roles, not raw endpoints or ticket
values. Do not publish an enriched operator manifest as a CI artifact.

## 4. Running existing safe Staging tests (operator action only)

Once an authorized operator has actually built a separate Staging
environment and confirmed no Production data or shared credentials:

- Configure the protected GitHub **`ACTIVA-Staging-ReadOnly` Environment**
  with required human reviewers and branch restrictions. The S2.11
  workflow does **not** create or verify those GitHub settings.
- Set managed approved Staging origins and an exact deployed source SHA
  in the environment; execute existing S2.11 `workflow_dispatch`
  manually. That workflow does only GET/OPTIONS with no cookies or tokens,
  and produces a sanitized automated result.
- Execute S2.10 physical Google Login/Android/iOS QR/Guest/Blind Review,
  campus network, privileged object scopes and independent penetration
  testing with permitted disposable accounts and controlled devices.
- Separately deploy the **Staging-only SIEM receiver**, verify request
  signing, durable and idempotent store, bounded signed ACK, HMAC rotation,
  outbound network restrictions, simulated crash/recovery and human
  responders. S3.5's sample code is not a deployed SIEM receiver.
- Preserve immutable institutional evidence for Security/Operations,
  and run S2.12 Production release-evidence review **only after** the
  institutional verification/independent approval process.

## 5. Explicit security design limitations and next decisions

- Application Postgres acts as a source and outbox but **is not independent
  append-only/immutable SIEM storage**; an operator-controlled external sink
  is required.
- Test-only 210 shared-IP Guests in CI do not prove real 200-person peak
  load, acceptable latency, WAF rules or regional failover.
- Domain-name syntax checks cannot prevent DNS rebinding or prove the
  legitimacy of a third-party receiver; use reviewed egress firewall rules.
- Even a cryptographically verified SIEM receipt does not prove that an
  authorized staff member viewed/handled the incident.
- Candidate source code and migrations are on unmerged Draft PRs.
  A repository owner and independent reviewers must choose a controlled
  review/integration plan; this script cannot merge them.
- Phase 4 institutional site authorization and research ethics are
  independent of all software security checks and remain **HOLD**.
