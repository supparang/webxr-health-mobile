# ACTIVA-AI S2.11 — Operator-controlled Staging acceptance workflow

**สถานะ:** เตรียมกระบวนการตรวจรับเท่านั้น — ยังไม่ได้ตรวจ Staging จริง
ยังไม่มีการ Merge, Deploy, เปิดใช้งาน Production หรือดำเนินการกับข้อมูลบุคคล

## สิ่งที่เพิ่ม

`.github/workflows/activa-ai-staging-acceptance.yml` เป็น GitHub Actions
ที่เรียกด้วย `workflow_dispatch` **ด้วยมือเท่านั้น** ไม่มีการเรียกจาก
push, pull request, schedule หรือ Production monitor

เมื่อได้รับอนุญาตจากผู้ดูแลแล้ว จึงใช้งานตัวตรวจ S2.10
`scripts/verify-staging-security.mjs` ทำเฉพาะ GET/OPTIONS แบบไม่ส่ง
credentials, ไม่ติดตาม redirect และไม่แก้ข้อมูลใด ๆ โดยตรวจ:

- เทียบ URL กับ Staging Origin ที่ผู้ดูแลกำหนดแยกต่างหาก
- ยืนยัน HTTPS, ชื่อ Staging, Source Commit ของ API ที่ Deploy จริง
- ป้องกันการนำ URL Production หรือ Localhost มาใช้แทน Staging
- ตรวจ Readiness, Authentication configuration, CORS,
  Security Headers, CSP บน HTML ทุกหน้าและค่า SHA-384 SRI
- ส่งออกข้อมูลรหัสรายการ PASS/FAIL และภาพรวมเท่านั้น
- `productionGoApproved:false`; `manualAcceptanceStatus:"NOT_TESTED"`
  เป็นค่าคงที่ของรายงาน เพื่อไม่ให้ CI อนุมัติใช้งานแทนบุคคล

## เงื่อนไขก่อนกด Run workflow

**GitHub Actions ที่สร้างใหม่บน Draft branch นี้ยังไม่สามารถนำไปใช้ใน
workflow_dispatch บน default branch ได้** จนกว่าจะผ่าน Review และ
Merge โค้ดที่เกี่ยวข้องอย่างถูกต้องตามลำดับ ห้าม Merge เพื่อ
เปิดใช้งาน Staging โดยข้ามการตรวจรับ PR เดิม

ผู้ดูแล GitHub Repository ต้องตรวจสอบและดำเนินการก่อน:

1. ยืนยันว่ามีเซิร์ฟเวอร์ **Staging ที่แยกจาก Production**
   และใช้ฐานข้อมูลทดสอบเท่านั้น
2. ตรวจ URL จริงและ SHA ที่ติดตั้ง ห้ามใช้ `activa-ai-production-api.onrender.com`
   หรือโดเมน Production อื่นใด
3. สร้าง GitHub Environment ชื่อ `ACTIVA-Staging-ReadOnly` และตั้ง
   **Required Reviewers**, Deployment Branch Restriction และผู้รับผิดชอบ
   ถ้าไม่มีการตั้งค่า Environment นี้ การระบุชื่อใน workflow
   *ไม่ได้รับประกันว่าจะมีการขออนุมัติจากผู้ตรวจ* จึงยังเป็น HOLD
4. ตั้งค่า Environment/Repository Variables ตามนโยบายสิทธิ์ของหน่วยงาน
   (ค่าดังกล่าวไม่ใช่ Secret และต้องไม่ใส่ข้อมูลบัญชีหรือ Token):
   - `ACTIVA_S211_APPROVAL_ENABLED=true` — เปิดหลังผ่านการอนุมัติเท่านั้น
   - `ACTIVA_S211_APPROVED_STAGING_ORIGIN` — HTTPS origin ที่อนุมัติจริง
   - `ACTIVA_S211_APPROVED_FRONTEND_ORIGIN` — HTTPS frontend origin
5. ก่อนเปิดอนุญาต ตรวจให้ตัวแปรสองค่าข้างต้นเป็น Origin ที่ถูกต้อง
   ไม่มี Userinfo, Path, Query, Fragment หรือข้อมูลส่วนบุคคล
6. ภายหลัง Workflow อยู่ใน default branch ที่ผ่าน Review แล้ว
   เข้า GitHub > Actions > ACTIVA-AI S2.11 Approved Staging Read-Only Acceptance
   > Run workflow แล้วกรอก `expected_source_commit` เป็น SHA 40 ตัวอักษร
7. อ่านผลใน Summary และดาวน์โหลด Artifact ชื่อ
   `activa-s2-11-staging-acceptance` (เก็บ 14 วัน)
   ถ้าไม่มีหลักฐานจากเซิร์ฟเวอร์ Staging จริง ให้คง `NOT TESTED`

ไม่มีการกำหนด URL Staging จาก Workflow Input เพื่อป้องกันผู้สั่งรัน
ชี้ปลายทางไปยังเซิร์ฟเวอร์อื่น รวมถึง Production โดยไม่ได้รับอนุมัติ
Workflow จะ Fail หาก `ACTIVA_S211_APPROVAL_ENABLED` ไม่เป็น `true`
หรือหากไม่ได้ระบุค่า Origin และ Commit ตามข้อกำหนด

**ข้อจำกัด:** ตัวแปร Environment/Repository เป็นการอนุมัติโดยผู้มี
สิทธิ์บริหาร GitHub ไม่ใช่หลักฐานพิสูจน์โดยอัตโนมัติว่าเซิร์ฟเวอร์
แยกฐานข้อมูลและข้อมูลบุคคลจริง ต้องมีหลักฐานกำกับจากผู้ดูแลระบบ

## การตรวจสอบด้วย CI

`tests/staging-dispatch-contract.mjs` ตรวจว่า Workflow:

- เรียกได้ด้วยมือเท่านั้น และไม่มี Trigger อัตโนมัติ
- ใช้สิทธิ์ `contents: read` และ Checkout เวอร์ชันจาก `main`
  โดยไม่เก็บ GitHub token ในไฟล์ Checkout
- ต้องมีค่า Approval Flag และ Origin ที่ผู้ดูแลกำหนดไว้ก่อน
- บังคับ SHA แบบ 40 ตัวอักษร และใช้ตัวตรวจ S2.10 ที่ไม่แก้ข้อมูล
- เก็บ Artifact แบบจำกัดอายุ และคงสถานะ Production HOLD

นี่คือการทดสอบโครงสร้าง Workflow **ด้วยข้อมูลจำลองและโค้ดบน CI**
ไม่ได้เป็นการทดสอบการ Run workflow จริงผ่าน GitHub Environment

## สิ่งที่ยังต้องทำก่อนปิด S2.11

- มี Staging จริงพร้อมหลักฐานว่าแยกจาก Production และ
  ใช้ข้อมูล/บัญชีทดสอบที่ได้รับอนุมัติ
- GitHub Environment ต้องตั้ง Required Reviewers และ Branch Restriction
  ให้ครบ และมีผู้ดูแลยืนยันตามบทบาทจริง
- Workflow ที่ผ่าน Review ต้องอยู่บน `main` และใช้กับ Commit ที่ Deploy
  ตรงกันโดยไม่ข้าม PR ที่รอตรวจ
- ได้ผลตรวจ PASS จริงจาก Approved Staging
- ดำเนินการ Manual Acceptance 13 ข้อตาม
  `docs/s2.10-real-staging-security-acceptance.md`
- ตรวจ Google OIDC/QR กล้องจริง รวมถึงแจ้งเตือนผู้ดูแลและ Security Review
