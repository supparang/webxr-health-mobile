## Private configuration

Copy `.env.pilot.example` to a private location outside the checkout, or enter its values directly in the hosting secret/configuration store. Keep the file readable only by the deployment operator. It intentionally contains blank values for:

- `DATABASE_URL`: a direct PostgreSQL connection suitable for migration DDL, with provider-required TLS. Keep the database private and restrict access to the backend and migration job. Use the same database/schema for both images. Follow the provider's CA verification instructions; never disable certificate verification to make a connection work.
- `QR_SIGNING_SECRET`: independent cryptographically random secret, at least 32 bytes of entropy, encoded as hex or base64.
- `RESEARCH_HASH_SALT`: a second independent cryptographically random secret, at least 32 bytes of entropy, encoded as hex or base64.

Generate and store these secrets privately; never paste them into chat, logs, GitHub Pages, `runtime-config.js`, build arguments or image layers. Preserve the research salt for stable pseudonyms; rotation requires a reviewed migration plan. No Google client secret is needed for this ID-token flow. Keep `ACTIVA_AUTH_MODE=GOOGLE_OIDC`, the explicit HTTPS origin allowlist, and `ACTIVA_PRODUCTION_GO_ENABLED=false`.

The public frontend may contain only the API HTTPS URL, release identity, deployment mode and public OAuth client ID/domain hints. Configure `apiBaseUrl` only after the backend URL is known and verified.

## Initialize the empty database

Run one release migration job with access to the private PostgreSQL service:

```sh
docker run --rm --env-file /secure/activa-backend.env activa-ai-migrate:1.0.15
docker run --rm --env-file /secure/activa-backend.env activa-ai-migrate:1.0.15 npm run prisma:status
```

The default migration command is `prisma migrate deploy`. The migration chain has a baseline followed by the original participant-response and position-title migrations. Re-running deploy is safe: only pending migrations run. It creates **no users, activities or demo data**.

Do not run `db:setup`, `db:push`, `prisma:migrate`, `db:reset-demo` or `prisma:seed` on this database. Those are development commands. The demo seed now refuses OIDC and production environments. `docker-compose.yml` is still a local synthetic-demo configuration with demo credentials and must not be used for a hosted pilot.

**Existing database warning:** the new baseline is for empty databases. If a database was previously created with `prisma db push`, or has historical migration rows, stop and take a verified backup. Compare its complete schema and migration history in a separate copy before a reviewed baselining plan. Do not mark migrations as applied blindly, modify the old migration SQL, force-reset data, or reuse an old demo volume as the pilot database. Local compose also expects a fresh schema or a separately reviewed migration history.


The command only creates the **first** ACTIVE ADMIN, records `ADMIN_BOOTSTRAPPED` in the same transaction, refuses identity conflicts, and refuses to elevate/reactivate existing records. Repeating the identical already-provisioned ADMIN returns without changing it. Once any administrator exists, use authenticated personnel administration for further users. The bootstrap command does not verify Google login ownership: the approved operator identity must be confirmed beforehand, then tested with a real Google login. It never approves Production GO.

Remove the one-time bootstrap variables/file from the deployment job after use according to the operator's secret-handling policy. Retain the audit entry.

## Launch the API and verify access

Configure the container platform to run the runtime image with the private backend environment, expose port `3000` through its HTTPS ingress, and probe `GET /api/health`. On a host with an HTTPS reverse proxy, the equivalent loopback binding is:

```sh
docker run --detach --name activa-ai-staging --restart unless-stopped --env-file /secure/activa-backend.env -p 127.0.0.1:3000:3000 activa-ai-api:1.0.15
```

For the actual HTTPS endpoint, verify:

1. `/api/health` succeeds, reports database `connected`, release `ACTIVA-AI-1.0.15`, Google OIDC configured and Production GO disabled.
2. The GitHub Pages frontend can reach it from the allowed origin and the backend rejects a different browser origin. The real frontend origin is also authorized in Google.
3. A request to `/api/me` without a token fails; demo identity headers alone fail. Invalid/expired tokens, wrong audience and disallowed Workspace domains fail.
4. The approved operator signs in through Google; `/api/me` maps to exactly the provisioned ACTIVE ADMIN. An approved-domain account absent from the database fails with `GOOGLE_ACCOUNT_NOT_PROVISIONED`; an inactive account fails. Do not store or share ID tokens.
5. Static requests for server code, Prisma files, package files and environment files expose no private backend content.
6. The release gate remains HOLD. Do not call the release-decision endpoint with `GO` or change the GO setting. Deployment and successful sign-in do not constitute release approval.

Capture only redacted acceptance evidence. Subsequent staging acceptance covers role boundaries, no self-review, QR expiry, attendance, audit, backup/restore and immutable closure using approved synthetic test records. Run the seeded smoke test only against its disposable CI database; never point it at the personnel database.

## Recovery and the remaining release decision

Before each future schema change, verify the provider's encrypted backup and point-in-time recovery configuration and test restoration into a separate database. The application backup checksum/recovery check is useful evidence but is not a substitute for an actual PostgreSQL restore test. If a deployment fails, keep traffic on the previous working app or HOLD it; do not issue a destructive database reset. Restore or reverse a schema change only through a reviewed recovery plan.

Production GO remains disabled until a separate explicitly authorized release decision after deployed authentication/access acceptance, backup restoration, privacy/retention governance and operational sign-off. This document does not grant that approval.

## Configuration and dependency evidence

`authentication.configurationReady` describes valid OIDC configuration only. The legacy `authentication.productionReady` field is retained for compatibility and has the same narrow meaning. Neither field confirms a real Google login, deployment approval or Production GO. The release gate includes `PRODUCTION_GO_DISABLED` by default; even ADMIN cannot record GO while that deployment setting is disabled.

The locked Prisma 6 toolchain uses a scoped `deepmerge-ts` 8.0.0 override to address [GHSA-ggr8-5vv4-36mx](https://github.com/advisories/GHSA-ggr8-5vv4-36mx). CI checks the dependency audit, Prisma generation, fresh/repeated migration, schema parity, bootstrap, both container targets and the existing application workflow. Review this override when upgrading Prisma.

OIDC regression tests use the real Google JWT verifier with ephemeral signing keys and a substituted certificate fetch; database identity behavior is tested with fixtures. They cover signature, audience, issuer, expiry, verified email, hosted domain, inactive/unprovisioned/ambiguous users and spoofed demo headers. They do not verify Google Cloud console settings or the actual institutional account. See [Google's server-side ID-token verification guidance](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token). Authentication currently follows the explicitly provisioned email mapping; operators must review account reassignments, and must not silently transfer access when an institutional email changes owner.
