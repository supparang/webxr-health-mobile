# ACTIVA-AI V1.0.16 — Neon PITR + Isolated Restore Drill

**Status:** Implementation ready for operator drill  
**Baseline:** `ACTIVA-AI-1.0.15` Production Acceptance Release  
**Safety rule:** Never use the Neon "Restore" action on the Production branch for this drill. Create a separate point-in-time branch and verify that branch only.

## Purpose

This drill proves that ACTIVA-AI production data can be reconstructed from Neon history into an isolated branch without modifying the live Production database.

The drill is intentionally read-only from ACTIVA-AI's perspective:

- no application writes;
- no Prisma migration deploy;
- no admin bootstrap;
- no Production GO/HOLD change;
- no QR secret rotation;
- no OAuth change;
- no participant-level export.

## Architecture

```text
Neon Production branch
        |
        |  create branch at selected historical timestamp
        v
Isolated recovery branch + independent compute endpoint
        |
        |  recovery connection string
        v
GitHub Environment secret: ACTIVA_RECOVERY_DATABASE_URL
        |
        v
ACTIVA-AI Neon Recovery Drill workflow
        |
        +-- target-is-Neon guard
        +-- recovery != production guard
        +-- reviewed migration set
        +-- required schema tables
        +-- exactly one ACTIVE ADMIN
        +-- ADMIN_BOOTSTRAPPED audit marker
        +-- no audit record after selected recovery point (+5 minute tolerance)
        |
        v
Non-PII recovery-verification.json artifact
```

## 1. Select a meaningful recovery point

Choose a timestamp inside the Neon history-retention window.

For a meaningful PITR test, choose a point before a known later operational event. Use Neon's Time Travel / historical query capability to confirm that the selected timestamp contains the expected earlier state before creating the branch.

Record the exact timestamp in UTC ISO-8601 form, for example:

```text
2026-09-30T12:20:00Z
```

Do not invent a timestamp. Use the exact timestamp selected in the Neon console.

## 2. Create the isolated Neon recovery branch

In Neon:

1. Open the ACTIVA-AI Production project.
2. Open **Branches**.
3. Create a **new branch** from the Production/main branch.
4. Select the historical **Time** / point-in-time option.
5. Enter the chosen timestamp.
6. Name the branch clearly, for example:
   `activa-recovery-drill-20260930`.
7. Create a compute endpoint for the branch.
8. Obtain that recovery branch's pooled PostgreSQL connection string.

Do **not** replace, reset, or restore the live Production branch during this drill.

## 3. Add the temporary GitHub recovery secret

GitHub repository:

`Settings -> Environments -> Production -> Environment secrets`

Create/update:

```text
ACTIVA_RECOVERY_DATABASE_URL
```

Value: the isolated recovery branch connection string only.

The existing `ACTIVA_PRODUCTION_DATABASE_URL` remains unchanged.

The workflow refuses to continue if recovery and Production resolve to the same Neon host + database.

## 4. Run the guarded workflow

GitHub:

`Actions -> ACTIVA-AI Neon Recovery Drill -> Run workflow`

Inputs:

```text
confirm = VERIFY-ACTIVA-NEON-RECOVERY
recovery_point_utc = <the exact Neon PITR timestamp>
```

The workflow performs only read operations against the recovery connection.

Expected PASS evidence:

- target is a Neon PostgreSQL endpoint;
- recovery endpoint is not the Production endpoint;
- current database matches the recovery URL;
- reviewed migrations are exactly:
  - `20260926000000_initial_baseline`
  - `20260927170000_participant_response_workflow`
  - `20260928094500_position_role_separation`
- required ACTIVA-AI tables are present;
- exactly one ACTIVE ADMIN exists;
- `ADMIN_BOOTSTRAPPED` audit evidence exists;
- latest restored audit timestamp is not later than the selected recovery point plus five minutes;
- verifier reports `productionTargetQueried=false`;
- a non-PII evidence artifact is uploaded.

## 5. Evidence to retain

Retain:

- Neon recovery branch name;
- selected UTC recovery timestamp;
- GitHub Actions run URL;
- successful job summary;
- `activa-ai-neon-recovery-evidence` artifact;
- screenshot of the Neon recovery branch showing it is separate from Production.

Do not copy the recovery database connection string into reports, screenshots, issues, or research artifacts.

## 6. Cleanup

After evidence is retained:

1. Delete the temporary `ACTIVA_RECOVERY_DATABASE_URL` GitHub Environment secret, or replace it only when the next controlled drill begins.
2. Delete the temporary Neon recovery branch/compute when no longer required.
3. Confirm the Production branch and Production connection string were never changed.
4. Run the normal ACTIVA-AI Production Monitor once more.

## PASS criteria

The drill is PASS only when:

- the recovery branch was created from the intended historical timestamp;
- the workflow passed all read-only structural/governance checks;
- recovery evidence was retained;
- the Production branch was never restored, reassigned, or mutated;
- the normal Production Monitor still passes afterward.

## HOLD criteria

Stop the drill and do not treat it as recovery evidence if:

- the recovery connection string equals the Production target;
- migration set differs from the reviewed release;
- required tables are missing;
- ACTIVE ADMIN count is not exactly one;
- `ADMIN_BOOTSTRAPPED` is absent;
- restored audit data extends beyond the chosen PITR point;
- operator cannot prove which timestamp/branch was used;
- Production availability or configuration changed during the drill.
