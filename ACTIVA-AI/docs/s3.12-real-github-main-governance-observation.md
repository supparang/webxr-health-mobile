## S3.11 detector weakness found and fixed

The preceding `probe-github-governance.mjs` only checked that **some** active branch ruleset appeared in the API response. That could wrongly label governance observation as complete when the ruleset targeted no known branch and required no human review.

S3.12 adds `scripts/github-effective-ruleset.mjs` and extends the read-only probe to:
- obtain **bounded per-ruleset details** from the same fixed approved GitHub REST host, using sanitized positive numeric IDs returned by the active ruleset list;
- require explicit recognized main targeting in the rule conditions and no exclusions before considering the rule applicable (unknown wildcards/exclusions stay **UNVERIFIED**, not automatically bad);
- observe that the listed bypass actors array is empty (even that is not full external bypass attestation);
- inspect a conservative policy bundle: two required pull-request approvals, code-owner review, stale-review dismissal, last-push approval, conversation resolution, required exact CI status, strict status policy, force-push/deletion controls;
- additionally check that the GitHub main branch API explicitly reports `protected: true`; a false value is not silently overridden by presence of an unrelated active ruleset;
- preserve the S3.11 **always HOLD** outcome and no raw API data, personal identities or secrets in reports.

The check currently requires the policy bundle to be observed in one explicitly targeted ruleset. GitHub can aggregate protections from multiple overlapping rulesets; therefore **false negatives are permitted** and must be independently adjudicated, whereas a weak or unscoped rule must never produce a false positive. GitHub itself describes effective rules as layered; an independently authorized administrator must inspect the effective result and bypass privileges.
