# ACTIVA-AI V1.0.15 — Backend Connection Layer

**Status:** Production Pilot Preparation  
**Release identity:** `ACTIVA-AI-1.0.15`

## 1. Goal

V1.0.15 separates the public browser client from the database boundary.

Correct architecture:

```text
Browser / Mobile
      |
      | HTTPS
      v
ACTIVA-AI Backend API
Node.js / Express
      |
      v
Prisma ORM
      |
      v
PostgreSQL
```

The browser must never connect directly to PostgreSQL.

## 2. Runtime modes

### Demo Mode
- Uses `demo-api.js`.
- Stores synthetic/demo state in browser `localStorage`.
- Does not require PostgreSQL.
- Cannot authorize Production GO.

### Pilot/API Mode
- Uses an explicit Backend API base URL.
- The API URL is public configuration and is safe to expose.
- Before login, the client calls `GET /api/health`.
- Pilot/API login proceeds only when:
  - the API is reachable,
  - `database === "connected"`, and
  - backend `releaseVersion` matches the frontend release when supplied.

## 3. Public runtime configuration

`runtime-config.js` contains public browser configuration only:

```js
window.ACTIVA_CONFIG = {
  releaseVersion: "ACTIVA-AI-1.0.15",
  apiBaseUrl: "",
  deploymentMode: "DUAL_DEMO_AND_PILOT_API"
};
```

Never place these values in `runtime-config.js`:
- `DATABASE_URL`
- database username/password
- QR signing secret
- research hash salt
- access tokens
- private keys
- any other credential

## 4. Backend environment variables

Server-side configuration remains in environment variables:

- `DATABASE_URL`
- `QR_SIGNING_SECRET`
- `RESEARCH_HASH_SALT`
- `RULE_VERSION`
- `REVIEW_TARGET_HOURS`
- `ALLOWED_ORIGINS`

`ALLOWED_ORIGINS` is a comma-separated browser-origin allowlist, for example:

```text
https://supparang.github.io,https://pilot.example.org
```

## 5. Connection safety

The browser stores only the selected API base URL in `sessionStorage`.

For Pilot/API Mode:
1. User supplies or deployment preconfigures the Backend API URL.
2. Client calls `/api/health`.
3. Backend verifies PostgreSQL connectivity with Prisma.
4. Client checks release compatibility.
5. Only then does the client request `/api/me`.

This prevents a frontend that says V1.0.15 from silently using an incompatible backend release.

## 6. Production deployment checklist

Before real personnel data is used:

1. Deploy the Node.js/Express API over HTTPS.
2. Provision PostgreSQL in an approved environment.
3. Set `DATABASE_URL` only in the backend secret store.
4. Set strong production `QR_SIGNING_SECRET` and `RESEARCH_HASH_SALT`.
5. Set `ALLOWED_ORIGINS` to approved frontend origins.
6. Run Prisma schema deployment.
7. Seed only approved pilot identities/data.
8. Verify `GET /api/health` reports database connected.
9. Verify frontend and backend release identities match.
10. Run role/RBAC, QR, attendance, audit, backup/recovery and immutable-closure acceptance against the deployed backend.
11. Complete PII governance, retention, backup-location and incident-response approval before Production GO.

## 7. Non-goals

V1.0.15 Backend Connection Layer does not itself authorize Production GO and does not mean real personnel data may be loaded. It establishes the safe connection boundary required for the next pilot-readiness tests.


## 8. Google Workspace authentication

Pilot authentication uses Google Identity Services / Google OIDC.

Flow:

```text
Google Workspace account
        |
        | Google ID token
        v
ACTIVA-AI Backend
  - verify signature
  - verify OAuth Client ID / audience
  - require verified email
  - require allowed Workspace hosted domain
        |
        v
Match existing User.email in PostgreSQL
        |
        v
ACTIVA-AI role + activity permissions
```

Required backend settings:

- `ACTIVA_AUTH_MODE=GOOGLE_OIDC`
- `GOOGLE_CLIENT_ID=<Google OAuth Web Client ID>`
- `GOOGLE_ALLOWED_DOMAINS=<approved Workspace domain>`

Security rules:

- Unknown Google accounts are rejected.
- Accounts are not auto-created from Google.
- Google authentication never grants ADMIN/STAFF/ORGANIZER automatically.
- The Google email must already be linked to an active ACTIVA-AI user record.
- Role and activity permissions remain controlled by ACTIVA-AI/PostgreSQL.
- `DEMO_HEADER` remains limited to CI/local demo use and is never production-ready.
