# ACTIVA-AI V1.0.16 Phase 2 — Production Operations & First Real Activity

**Status:** In progress  
**Baseline:** ACTIVA-AI-1.0.15 Production Acceptance Release  
**Principle:** Phase 2 must not rewrite V1.0.15 release evidence. It adds post-release operational verification and prepares a controlled first real activity.

## 1. Phase 2 objectives

1. Detect production liveness/readiness regressions without exposing PII or credentials.
2. Preserve governance invariants after release:
   - deployment tier remains PRODUCTION;
   - PostgreSQL remains connected;
   - Google OIDC remains production-ready;
   - release identity remains the accepted baseline until a new release is formally cut;
   - autonomousDecision=false.
3. Establish a repeatable First Real Activity acceptance protocol before scaling use.
4. Collect operational evidence separately from research outcome data.

## 2. Automated production monitor

Phase 2 adds:

- ACTIVA-AI/scripts/verify-production.mjs
- GitHub Actions workflow ACTIVA-AI Production Monitor

The monitor runs every six hours and can also be dispatched manually. It probes only:

- GET /api/live
- GET /api/ready
- GET /api/health

It verifies the accepted production invariants and exits non-zero on regression. The monitor deliberately does not authenticate as a person, mutate data, print OAuth client IDs, or access participant-level records.

A failed scheduled run is an operational signal requiring investigation; it is not an automatic personnel or release decision.

### GitHub alert routing

Production monitor failures now create or update one persistent GitHub incident titled `[PRODUCTION ALERT] ACTIVA-AI monitor failure`.

Alert behavior:
- the incident is assigned to `supparang` so GitHub can surface a direct notification;
- repeated failures append to the same open issue instead of creating issue spam;
- the alert includes only UTC time, expected release, production endpoint, workflow run URL and commit SHA;
- participant data, OAuth tokens, database credentials and other secrets are never added to the issue;
- a subsequent successful monitor run posts a RECOVERED comment and automatically closes the incident;
- the workflow still ends in failure after creating/updating the incident, preserving GitHub Actions failure visibility.

Manual `workflow_dispatch` includes an optional `simulate_failure` input for alert-routing verification. This synthetic failure does not mutate Production. Run a normal successful monitor immediately afterward to verify automatic recovery/closure.

## 3. First Real Activity acceptance

Run one controlled real activity before broad rollout.

### Preconditions

- current production release remains GO;
- /api/live and /api/ready pass;
- backup/recovery verification is current;
- approved users are provisioned explicitly;
- participant notice/consent and organizational approval are complete where required;
- no synthetic/demo identities are mixed with real activity records.

### Golden operational flow

1. ADMIN/ORGANIZER creates one activity with approved scope and policy.
2. Assign only the minimum required organizer/reviewer roles.
3. Participant performs Dynamic QR Check-in.
4. Participant performs Dynamic QR Check-out.
5. Evidence Engine evaluates the attendance record.
6. Human Review is performed only when workflow/evidence requires it.
7. Final human decision is recorded with reason where required.
8. Activity reaches close-ready state.
9. ADMIN records Immutable Closure.
10. Audit Trail is reviewed end-to-end.
11. Pilot Readiness/operational monitoring returns no critical data-quality alert.
12. Export only approved aggregate/de-identified research evidence.

### Acceptance evidence to retain

- activity identifier and timestamps;
- screenshots of lifecycle status without unnecessary PII;
- Audit Trail event sequence;
- evidence-status/final-decision separation;
- immutable closure hash;
- production monitor run URL/result;
- backup/recovery verification timestamp;
- incident notes if any exception occurred.

## 4. Stop conditions

HOLD the real-activity rollout if any of the following occurs:

- /api/ready fails;
- database connectivity is unavailable;
- authentication readiness fails;
- deployment tier is not PRODUCTION;
- critical data-quality alert appears;
- review backlog breaches the approved operational target;
- ended activity cannot be immutable-closed;
- audit evidence is missing for an irreversible action;
- AI is observed changing a final personnel decision autonomously.

## 5. Not yet completed in Phase 2

The following remain provider/governance work and are not solved by the monitor alone:

- provider-level PostgreSQL PITR and an isolated restore drill;
- optional secondary alert destination beyond GitHub and formal escalation ownership;
- log retention/redaction approval;
- custom production domain/TLS if required;
- production user provisioning/deprovisioning runbook;
- secret rotation drill;
- dependency/runtime patch cadence.

AI/XAI deployment remains a later research phase. Human Final Decision remains authoritative.
