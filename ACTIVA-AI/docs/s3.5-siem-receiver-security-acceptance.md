# ACTIVA-AI S3.5 — SIEM Receiver Authentication & Operational Acceptance

**Current recommendation: HOLD / NO-GO.** S3.5 is a reviewable
security-code candidate. It does not establish an institutional SIEM,
real external log ingestion, an immutable audit trail, or permission to
deploy to Production. Draft PRs S2.1–S3.4 remain unmerged.

## 1. Defect addressed

Before S3.5 the application accepted a 200/202 HTTP response containing
`accepted:true`, its own event ID and an arbitrary-looking receipt ID
as proof of SIEM ingestion. While HTTPS authenticates the TLS endpoint
under a trusted certificate, **a valid-looking JSON response alone is not
cryptographic proof that the intended SIEM receiver issued it**. A wrong
service at a misrouted endpoint could present a plausible receipt.

The prior receiver also called `response.text()` and checked only the
size *after buffering* the complete response. An unexpected very large
response could consume excess application memory.

## 2. S3.5 wire protocol

The S3.4 outgoing POST remains unchanged:

- Exactly `POST {ACTIVA_SIEM_EXPORT_ORIGIN}/v1/activa-security-events`
- `Content-Type: application/json`
- `X-Activa-Event-Id: ACTIVA-S34-<32 lowercase hex>`
- `X-Activa-Signature-SHA256:` HMAC-SHA256 of exact outgoing JSON bytes,
  keyed with the separate outbound SIEM shared secret
- `redirect:error`, HTTPS-only approved origin, five-second timeout

**New receiver-side response contract**:

1. The receiver must independently authenticate the request signature
   and check the event ID, schema, allowlisted category and strict field set.
2. The receiver must perform **durable, atomic, idempotent ingestion**
   keyed by the event ID. A replay with the **same exact message** must
   return the original receipt; a replay with different message bytes for
   the same ID should return a conflict and alert operations.
3. Once the transaction commits, the receiver returns HTTP **200 or 202**
   with at most **4096 bytes** of JSON:
   `{"accepted":true,"eventId":"ACTIVA-S34-...","receiptId":"opaque-id"}`.
   The object must have exactly those three fields.
4. The receiver must add a response header
   `X-Activa-Ack-Signature-SHA256`, computed as:

```text
HMAC_SHA256(
  ACTIVA_SIEM_EXPORT_HMAC_SECRET,
  ASCII("ACTIVA-AI-SIEM-ACK-V1\n") || exact UTF8 response JSON bytes
)
```

5. ACTIVA-AI verifies the 64-hex lower-case HMAC in constant time before
   parsing the JSON. It also checks the exact `eventId`, bounded
   `receiptId`, valid UTF-8 and 200/202 status. The receiver must send
   a streaming response (ordinary HTTP response bodies satisfy this).
6. The client **streams** the JSON with a hard 4096-byte cap; it never
   buffers an unbounded `response.text()` before checking length.

**Any missing, forged, malformed, oversized or mismatched receipt
returns the existing pending/retry state.** No SIEM receipt alone
means that an incident was investigated or human-acknowledged.

The response HMAC is domain-separated from the request HMAC, preventing
a request signature from being reflected as a valid acknowledgment.

## 3. Security and limitations

Two-way HMAC authenticates *possession of the configured secret*, not
institutional ownership, audit immutability or staff acknowledgment.
If the secret is compromised, an attacker could forge both directions
of the protocol. Use a dedicated secret-manager value, restrict access
to the application and the receiving integration, and rotate with a
documented overlap/revocation plan.

- The configured hostname and origin still require **independent
  DNS/TLS ownership verification, an outbound egress firewall with
  deny-private-network controls, and monitoring against DNS rebinding**.
  Static URL validation alone cannot prevent SSRF.
- Deploy the receiver independently of ACTIVA-AI's database and
  administrative identity. A test mock is not a SIEM product.
- Receiver receipts must not expose employee identities, participant
  records, QR secrets, raw IPs, credentials or bearer tokens.
- The sender still exports threshold-level de-identified summaries,
  not a full WAF/CDN or privileged-audit event stream.
- Delivery semantics remain **at least once**: receiver-side event-ID
  uniqueness is mandatory. A successful remote commit followed by a
  crash before the sender marks delivered may trigger a retry.
- Capacity planning, encrypted retention, access monitoring, incident
  escalation, restoration and real operator ACK require independent
  organizational evidence.

## 5. Test-only evidence

`tests/siem-receipt-security.mjs` implements a standalone, independently
calculated HMAC receiver contract with an in-memory deduplication map,
plus negative signature/body/replay/privacy tests. The prior
`tests/security-siem-export.mjs` now uses authenticated responses and
continues to validate real disposable PostgreSQL retry and lease state.

- No real institution SIEM host or service is provisioned or contacted.
- No Production URL, Live GO, cloud secrets or deployment workflow runs.
- CI successes are software checks, not operator or research permissions.

**Production Security Acceptance: HOLD / NO-GO. Phase 4 research ethics:
independent HOLD.**
