# ACTIVA-AI S2.4 — Security Alert Delivery via GitHub Issues

**Status:** Draft / opt-in only. This change builds on unmerged S2.3 PR #138.
It does **not** deploy to Production or change the PostgreSQL schema.

## Objective

S2.3 can emit a privacy-safe `security_alert` log event. S2.4 optionally routes
these events into the existing GitHub Issues operational alert channel, where
incident owners can be assigned and GitHub notifications may be delivered
according to their own notification preferences.

A successful GitHub API response proves only that GitHub accepted an Issue or
comment. It does **not** prove a human read, acknowledged, or resolved the alert.

## Delivery design

- Fixed API destination: `https://api.github.com`; no arbitrary webhook URLs.
- Categories sent: `AUTH_DENIED`, `ACCESS_DENIED`, `RATE_LIMITED`, `SERVER_ERROR`.
- One open Issue per category (stable title). Subsequent alerts post a comment
  on that Issue while open. This reduces issue flooding but is not an atomic
  multi-instance deduplication guarantee.
- The S2.3 monitor emits each threshold alert only once per category per
  15-minute window **per Node.js process**.
- Asynchronous, nonblocking delivery; maximum four in-flight attempts/process;
  4-second deadline per GitHub API call, no redirects with credentials.
- If GitHub returns an error or transport fails, emit a privacy-safe
  `security_alert_delivery` failure record to provider logs. No raw API
  response, request body, token or GitHub authorization headers are logged.
- Do not retry ambiguous issue/comment POST requests automatically: retries
  after response loss can create duplicate Issues or comments. The existing
  security alert log remains the fallback investigation evidence.
- No local persistent queue: process restart or prolonged GitHub outage may
  lose external alert delivery. Provider log alerts/SIEM or a durable queue are
  required for enterprise-grade guaranteed delivery.

## Safe configuration

By default `ACTIVA_SECURITY_ALERT_MODE=DISABLED`; no outbound network calls.

Only after operator approval, in the **hosting provider's private secret store**
and in the specific reviewed environment:

```dotenv
ACTIVA_SECURITY_ALERT_MODE=GITHUB_ISSUE
ACTIVA_SECURITY_ALERT_GITHUB_REPO=supparang/webxr-health-mobile
ACTIVA_SECURITY_ALERT_GITHUB_ASSIGNEE=supparang
ACTIVA_SECURITY_ALERT_GITHUB_TOKEN=<private-fine-grained-issues-token>
```

The token must be created for the **target repository only** with **Issues
read/write** permissions, preferably short expiration and periodic rotation.
Never paste actual tokens into a chat, repository, browser script, issue,
frontend `.env` or CI workflow. GitHub Issues must be enabled and the bot/token
holder must have permission to create issues, read open issues and comment.

Configuration validation rejects invalid modes, malformed repository/assignee,
and absent/placeholder token **if delivery is explicitly enabled**. Existing
Production deployments with mode disabled are not blocked by this draft code;
this is **not** evidence of Production alert readiness.

The GitHub issue body deliberately contains *only*: anomaly category, severity,
UTC time, 15-minute count and threshold, plus response instructions. It contains
**no** client IP, user/email/employee ID, personal QR/Guest Pass token, full
request URL, request body or confidential activity data.

## Staging acceptance (not yet completed)

1. Confirm security incident owner, backup contact, GitHub Issue visibility,
   token ownership and authorized access.
2. Provision the minimal-scope token privately on **Staging only**, with
   `ACTIVA_PRODUCTION_GO_ENABLED=false`.
3. Generate a synthetic threshold crossing using disposable test data and
   inspect the resulting `[SECURITY ALERT] ACTIVA-AI ...` GitHub Issue.
4. Verify that assignment actually notifies the designated responder and that
   the responder can acknowledge and close the Issue.
5. Cross a second 15-minute window to verify an existing open Issue receives
   a comment rather than a new Issue.
6. Simulate a GitHub API outage/403. Confirm the failure appears in the
   protected provider logs and a fallback on-call channel can still notify.
7. Confirm log retention, GitHub Issues visibility, token rotation, rate limits,
   multiple instances and privacy approval. Perform end-to-end integration with
   #136, #137 and #138 before Production acceptance.

## Verification

- `node tests/security-alert-delivery.mjs`: mock-only GitHub API tests of
  Issue creation/comment reuse, no secret leakage, input validation, no
  requests when disabled, bounded queue, failure isolation and S2.3 threshold
  deduplication. Does not create any real GitHub Issues.
- CI passes required before review; also retain manual Staging delivery
  evidence. Full load tests and provider-side alert configuration are not
  provided by a passing CI run.

**Production Security Acceptance: HOLD** until actual alert delivery and
human acknowledgment are verified with the intended destination. Phase 4
human-subject research authorization remains independently HOLD.
