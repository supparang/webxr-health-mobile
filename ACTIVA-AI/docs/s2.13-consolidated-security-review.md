# ACTIVA-AI S2.13 — Consolidated Security Review Candidate

**Status: DRAFT — for independent review only; no merge, no Production deploy, no real Staging calls.**  
**Technical release recommendation: NO-GO / HOLD.**

## Purpose

ACTIVA-AI has proposed security fixes across S2.1–S2.12 in PRs
[#136](https://github.com/supparang/webxr-health-mobile/pull/136)–[#147](https://github.com/supparang/webxr-health-mobile/pull/147).
Most PRs target another unmerged security branch instead of `main`.
That is useful for small reviews but makes it hard to assess the entire
security change set, review cross-feature behavior and plan a controlled
release.

**S2.13 provides one additional consolidated `main`-targeting Draft PR
containing the entire cumulative security candidate for review**.
It does not supersede reviews of the source PRs; the source PRs remain
open and unmerged until humans reconcile/close them.

## Testable integration properties

A new `tests/security-consolidation-gate.mjs` checks the actual
combined source tree, in addition to the existing unit/browser/smoke
suites:

- Guest and Blind Review public IP/pass limiters run **before**
  `express.json` and authentication middleware.
- Authenticated actor/write limiters run **after** `attachActor`.
- Security event monitoring, redacted route logging, and alert dispatcher
  stay connected; aggregated security summary requires `ADMIN`.
- Attendance/evidence/personal QR scoping and Production rate-limit
  fail-closed guard are still present.
- Frontend CSP, anti-framing and both real-byte-pinned QR SHA-384 SRI
  script tags remain intact.
- S2.10 Staging checker and S2.12 release evidence evaluator always
  report Production approval false; the current S2.12 evidence template
  requires all M01–M13 manual checks.
- S2.11 workflow stays opt-in/manual-only rather than automatically
  probing any unknown or Production origin.

**This is a source-level integration inventory test, not a proof that
the application cannot be exploited.** Functional CI regression,
full code review and actual authorized Staging acceptance are separate.

## Proposed human review process

1. Open the **S2.13 consolidated Draft PR against `main`**
   and inspect **Files changed**, not just historical CI results.
2. Review each security component by section and cross-check source PRs
   #136–#147. Request independent Application Security + Privacy/PDPA
   + Operations reviews according to organization policy.
3. Confirm final staged stack is tested at an exact SHA. No security
   reviewer should approve release based solely on CI from earlier
   commits/branches.
4. Request audited Staging infrastructure from operations, then
   complete the S2.10/S2.11 real Staging workflow and manual M01–M13.
5. Resolve changes and update the final candidate; re-run full CI and
   have repository owner approve a controlled merge approach.
6. Only **after** organizational security acceptance consider a
   Production deployment decision; ethics research approval is separate.

**S2.13 exit criterion:** one reviewable full-stack Draft PR plus full
CI and a verifiable gap/owner register. **It is not a Production GO.**

**Production Security Acceptance: HOLD. Research Phase 4: HOLD.**
