# ACTIVA-AI P3.2.2 — QA Data Isolation

**Purpose:** prevent acceptance-test, synthetic/demo, and legacy/unclassified data from entering scientific Phase 3 evidence.

## Activity classification (database field, not inferred from activity title)

| Classification | Research cohort | Operational Ground Truth / Audit | How set |
| --- | --- | --- | --- |
| `QA_TEST` | NEVER | Retained | ADMIN on activity creation; known legacy QA backfilled by migration; one-way quarantine |
| `EMPIRICAL` | Eligible after actual LOCKED review | Retained | ADMIN at creation, with attestation and future activity start |
| `UNCLASSIFIED` | NEVER | Retained | Default for every legacy activity and non-admin-created activity |

**No API may promote an existing activity to EMPIRICAL.** Generic PATCH forbids editing research class. An ADMIN may irreversibly downgrade any activity to QA_TEST with at least 10 characters of documented reason; audit action `ACTIVITY_QUARANTINED_QA`. This also withdraws any pre-existing locked case belonging to that activity from research queries, without deleting audit history.

## Existing Production acceptance test

Migration `20261001133000_activity_research_classification` backfills only the exact known record matching:
- title `ACTIVA Phase 3 Blind Review QA`
- location `QA Test`
- category `วิจัย`

All remaining historical rows default to `UNCLASSIFIED` and are ineligible for scientific research. No legacy activity is automatically promoted to EMPIRICAL.

## Enforcement locations

- `GET /api/ml/readiness` — empirical-only labels and locked counts; operational Ground Truth Workspace stays all-data.
- `GET /api/ml/planning-summary` — empirical-only locked cases and prevalence.
- `GET /api/ml/dataset` — empirical-only, non-voided LOCKED cases; includes `dataProvenance`, `scope`, `data_classification`.
- `GET /api/research/export` — empirical-only, non-voided records (separate from ADMIN operational backup).
- `GET /api/ml/inference-dataset` — empirical-only unscored records.
- `GET /api/analytics/verified` — operational counts remain organization-wide; `researchSnapshot` includes EMPIRICAL rows only.
- `validate-phase3-dataset.mjs` — fail if payload provenance/scope missing or any record is non-empirical.
- `train_baselines.py` — rechecks same conditions before empirical model fitting. Synthetic CI pipeline remains a separate software-only path.

## How ADMIN creates a new empirical activity

Go to **กิจกรรม → สร้างกิจกรรม**. Under **ประเภทข้อมูลสำหรับ Phase 3** choose `EMPIRICAL`, check the research-provenance attestation, set activity start later than now, then create. The event still requires real attendance, two independent human labels, and lock to enter the ML dataset. If purpose is acceptance testing, select `QA_TEST` instead.

**Do not mark previously collected data as EMPIRICAL after reviewing outcomes.** If data were collected before this guard, keep them UNCLASSIFIED unless a separately documented scientific protocol amendment and independent provenance assessment establishes a lawful, defensible process (not supported by the automatic API).

## Production rollout (order matters)

1. Merge *migration workflow only* into main; it pins the reviewed migration commit.
2. ADMIN runs the guarded Production workflow. It checks the four current migrations, applies the additive fifth, verifies exact title/location/category QA backfill.
3. Only after successful migration, merge application PR and let Render deploy main.
4. Re-open the old QA record in Ground Truth: it must still exist as an operational case, but Planning Summary, ML dataset and Research Export must exclude it even if someone locks it.
5. Do not run Production empirical training or approve the sample plan based on QA/UNCLASSIFIED data.

## Validation

CI includes: Prisma migration/schema diff, synthetic operational flow, QA locked exclusion, UNCLASSIFIED locked exclusion, one-way quarantine, provenance attestation, and ML dataset + trainer rejection guards. These are software acceptance tests, **not** empirical study observations.
