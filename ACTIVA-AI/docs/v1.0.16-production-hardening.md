# ACTIVA-AI V1.0.16 — Production Hardening

**Status:** In progress  
**Baseline:** V1.0.15 Pilot Acceptance completed and preserved on `release/v1.0.15-pilot-accepted`.  
**Development branch:** `codex/activa-v1.0.16-production-hardening`.

## Purpose

V1.0.16 moves operational deployment controls beyond the accepted V1.0.15 pilot baseline without changing or reopening the immutable Test 01–03 evidence. The first hardening pass introduces an explicit deployment tier, prevents a staging deployment from enabling Production GO, and strengthens browser-facing security headers.

## Deployment separation

Use physically/logically separate services and databases:

| Tier | Branch / source | Database | GO behavior |
| --- | --- | --- | --- |
| Accepted baseline | `release/v1.0.15-pilot-accepted` | retained pilot baseline | historical evidence only |
| Staging | V1.0.16 development commit | staging PostgreSQL | must remain disabled |
| Production | reviewed V1.0.16 release commit | separate production PostgreSQL | initially disabled; enable only after production acceptance |

Do not point staging and production at the same `DATABASE_URL`. Generate independent `QR_SIGNING_SECRET` values. Preserve each environment's `RESEARCH_HASH_SALT` according to its pseudonymization/retention plan and never copy production personnel data into staging.

## New deployment-tier guard

Set exactly one of:

```text
ACTIVA_DEPLOYMENT_TIER=STAGING
ACTIVA_DEPLOYMENT_TIER=PRODUCTION
```

If omitted, the server defaults to `STAGING` for backward compatibility. Invalid values fail production startup configuration checks.

For `STAGING`, `ACTIVA_PRODUCTION_GO_ENABLED=true` is rejected as unsafe configuration. In addition, the release-decision endpoint blocks a GO decision unless the server is running with `ACTIVA_DEPLOYMENT_TIER=PRODUCTION`.

This separates **acceptance of a release candidate** from **authorization to run production traffic**.

## Browser security baseline

All responses add:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(self), microphone=(), geolocation=()`
- `Cross-Origin-Opener-Policy: same-origin-allow-popups` to preserve Google Identity Services popup behavior
- `X-DNS-Prefetch-Control: off`

Production-tier responses additionally send `Strict-Transport-Security: max-age=31536000`. A full CSP is intentionally deferred until Google Identity Services, QR libraries, inline scripts/styles and every required source have been inventoried and tested; deploying an untested CSP could break sign-in or QR scanning.

## Production configuration

Use `.env.production.example` only as a key/template reference. Filled values belong in the hosting platform's secret store.

Before creating a production service:

1. create a separate production PostgreSQL database and confirm encrypted backups/PITR;
2. create production-only QR signing and research hash secrets;
3. set exact HTTPS `ALLOWED_ORIGINS`;
4. configure the approved Google OAuth audience and identity allowlists;
5. provision only approved ACTIVE users; Google sign-in must never auto-create roles;
6. keep `ACTIVA_PRODUCTION_GO_ENABLED=false` during deployment and acceptance;
7. run migrations once from the reviewed release image;
8. verify health, CORS, OIDC, role boundaries, immutable closure and a real PostgreSQL restore into an isolated recovery database;
9. record production acceptance evidence;
10. only then set `ACTIVA_PRODUCTION_GO_ENABLED=true` and record the production GO decision.

## Remaining V1.0.16 work

- provider-level automated PostgreSQL backup/PITR and restore drill evidence;
- uptime/error monitoring and alert destination;
- log retention/redaction review;
- production domain/TLS and exact CORS/Google origins;
- production user provisioning/deprovisioning runbook;
- secret rotation procedure;
- dependency/runtime patch policy;
- final production acceptance test and release tag.

AI/XAI deployment remains a later research phase. Production hardening does not authorize autonomous personnel decisions; Human Final Decision remains authoritative.
