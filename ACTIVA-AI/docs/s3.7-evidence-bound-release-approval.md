# ACTIVA-AI S3.7 — Evidence-Bound Dual-Authority Release Control

**Scope:** Correct a source-level Production governance gap in S3.1.
**Status:** Draft code and synthetic CI verification only. Real Staging
and the institutional security evidence dossier have **NOT** been
verified or signed. **Production: HOLD / NO-GO.**

## Finding and security impact

The S3.1 Ed25519 release authorization signed the deployed commit,
expiry and nonce but **not the acceptance evidence package**. Two
signers could sign the correct code revision while later changing or
substituting the Staging evidence dossier without invalidating the
release signatures. Merely having a code commit and two signatures
does not demonstrate what the people reviewed.

S3.7 makes the **exact evidence-dossier byte digest** and the **Staging
deployed commit** part of the data covered by both signatures. If the
evidence file changes, or the installed commit differs from the commit
actually tested on Staging, both signatures become invalid. A V1
signature is no longer accepted.

## Mandatory V2 protocol

Both distinct Security and Operations authorities must sign these
UTF-8 bytes, in this **exact order**, with LF between lines and a
final LF at end:

```text
ACTIVA-AI-PRODUCTION-SECURITY-GO-V2
<40 lower-case hex Production deployed commit>
<40 lower-case hex approved Staging deployed commit>
<64 lower-case hex SHA256 of reviewed evidence dossier>
<strict UTC expiry ISO 8601 timestamp>
<lower-case hex nonce (32–128 characters)>
```

The verifier requires `RENDER_GIT_COMMIT`,
`ACTIVA_RELEASE_APPROVED_COMMIT` and
`ACTIVA_RELEASE_STAGING_COMMIT` to be the **exact same SHA**,
requires `ACTIVA_RELEASE_STAGING_EVIDENCE_SHA256` to be a valid 64
lowercase hex digest, and verifies two **different** Ed25519 public
signing identities against the canonical V2 message. Each signature
still expires within the 24-hour maximum approval window. Existing
key custody/rotation controls and startup + ADMIN release gate remain.

A signed V1 message or unchanged V2 signature paired with a
different dossier hash, Staging SHA, expiry or nonce **must fail
closed**. No private signing key is checked in or generated by this PR.

## Procedure for an institution-authorized reviewer (NOT EXECUTED)

1. Identify the **final exact deployed release commit** after the
   approved GitHub change process. If a merge or build step creates
   a different commit, install/test that **same final commit** on
   isolated Staging. Do not assume the draft PR SHA will be the
   eventual Production commit.
2. Independently review S3.6 infrastructure isolation and all
   S2.10 M01–M13 plus S3.5 S35-M01–M12 acceptance tests against
   the approved Staging system. Review the SIEM real receipt, human
   on-call acknowledgment, API authorization, network, database,
   secrets, retention, backup/restore, privacy and P0 findings.
3. In a protected institutional record store, freeze an
   immutable, versioned evidence dossier (including approved
   provenance records and report of critical/high findings).
   Obtain its SHA-256 over **the exact bytes**. A mutable ticket
   URL or the S3.6 synthetic template is NOT an evidence dossier.
4. Security and Operations **separately** inspect that exact
   dossier and commit. Verify institutional authorization and
   ownership of independently held Ed25519 keys. Record their
   decision and authenticated timestamps in the institution's
   governance system.
5. If both independently authorize the release, sign the same
   canonical V2 bytes. Store only public keys, expiration,
   signatures and the dossier **hash** in the protected deployment
   secret/approval configuration. Do not put dossier contents,
   participant details, signing private keys, or secrets in GitHub
   Actions logs or public repository files.
6. Before any Production GO decision, perform an independent
   source/evidence match and verify no critical/high finding is
   unresolved. Change in dossier bytes, staging SHA, deployed SHA
   or authorizer identity requires another review and both new
   signatures. Practice approval expiry, rollback and startup
   restarts on isolated Staging.

## Real-world limitations (remain open)

**A cryptographic hash is not proof that an evidence document is true.**
The application accepts the digest supplied via an authorized
deployment configuration; it does not fetch a protected institution
record, verify human reviewer identity, prove signers are independent
people, or establish physical SIEM/WAF ownership.

The S3.6 offline manifest remains `decision: HOLD` even when
synthetically filled. It cannot be used as a substitute for 25
independently reviewed manual Staging checks. This change is a defense
against accidental evidence substitution, not permission to collect
human-subject data or open Production.

**Release status: NO-GO/HOLD. Research ethics: separate HOLD.**

## Software regression evidence

The expanded `tests/production-security-architecture.mjs` uses
ephemeral Ed25519 keys in CI to test:
- positive V2 dual-signer message with exact staging/release SHA;
- missing, malformed, changed or differently cased evidence hash;
- changed/missing Staging commit;
- rejection of both validly signed *legacy V1* authorizations;
- all earlier mismatched deployment SHA, stale expiry,
  duplicate signers, forged signatures and DB TLS failures.

These are source-level synthetic tests only; no actual institutional
signatures were requested or created.
