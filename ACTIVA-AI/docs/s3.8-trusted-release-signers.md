# ACTIVA-AI S3.8 — Release Signer Identity Trust Anchors

**Status (15 October 2026): DRAFT, SOFTWARE TESTS PENDING, NO DEPLOY / NO MERGE. Production remains HOLD/NO-GO.**

## Why S3.7 was insufficient

S3.7 verifies two valid Ed25519 signatures over the exact deployed commit and Staging dossier hash. But the application also obtained **both verifying public keys from the same deployment environment** as the signatures. Anyone who can edit all deployment environment variables could create two fresh key pairs and signatures, replace the corresponding public keys, and satisfy cryptographic signature verification without the institution's designated Security and Operations authorities. *Two signatures do not establish two trusted human authorities.*

## S3.8 source-level countermeasure

- `server/release-authority-trust.js` defines two role-specific **SHA-256 hashes of Ed25519 SPKI DER public keys**; **both are currently null**. Unlike deployment environment variables, these values must be enrolled only through independently reviewed changes to protected source.
- `productionReleaseApproval()` continues validating the exact source SHA, Staging evidence SHA-256, strict expiry/nonce, different Ed25519 keys and both V2 signatures. After signature verification, it additionally requires two valid, distinct **pre-enrolled source pins** and constant-time matches against the corresponding DER SPKI key hashes.
- A signer that possesses a valid signing key but is **not enrolled for its role** fails closed. Replacing both public keys and both valid signatures in environment variables also fails closed. Swapping Security and Operations roles fails closed.
- Unit tests provide their own ephemeral local-only trust pins as a non-production function argument; this is **not wired to HTTP, environment configuration or the server**. No CI-generated identity can enroll into Production.

## Institutionally controlled enrollment (NOT YET EXECUTED)

1. Obtain written authorization naming separate Security and Operations approvers and two independent private-key custodians. Each custodian generates/protects their Ed25519 private key **outside GitHub, CI, application runtime and deployment admin access**.
2. Independently authenticate each custodian's SPKI **public** key, verify role ownership and separation of duties, and calculate SHA-256 over the **raw DER SPKI bytes**. One example for a reviewed PEM public key: `openssl pkey -pubin -in approved-public.pem -outform DER | openssl dgst -sha256`. Repeat independently and compare in a restricted institutional change record.
3. Through a protected branch and mandatory independent code review, replace the two null pin values in `server/release-authority-trust.js` with the approved **lowercase 64-character SHA-256 fingerprints only**. Never commit private keys, approval signatures, real evidence dossiers, identifiable participant data or passwords.
4. Require repository branch protection/CODEOWNERS or an equivalent separately controlled approval path: deployment administrators alone must **not** be able to modify the trust-anchor source or bypass required Security/Operations reviews. Review deploy access and GitHub administration privileges; where one individual controls both code and deployment, source pinning **alone is not independent governance**.
5. Rebuild/review the exact final commit, retest on institution-owned isolated Staging, repeat all 25 manual acceptance cases, obtain external SIEM receipts and independent evidence-provenance review. Security and Operations sign the **same S3.7 V2 message** for the final exact commit and reviewed immutable dossier.
6. Enforce dual-controlled emergency revocation and rotation: remove/revoke the old fingerprint via separately reviewed code change, redeploy/retest Staging and issue new short-lived signatures. A compromised key or reviewer authorization must trigger **HOLD** and incident response, not an automatic key swap.

## Explicit limits / independent evidence required

- Current source pins are deliberately null: **real Production GO cannot pass even with syntactically valid signatures**. This is an intended secure default, not an operational signoff.
- A repository edit that removes this guard, a malicious deployment of different code, compromised GitHub administration, or a signer willingly issuing bad approvals are **outside** what two source-level hashes prevent. Enforce protected branch, independent release audit, exact deployed SHA attestation and human governance.
- An SHA-256 fingerprint identifies key bytes, not a human or a trustworthy acceptance document. External institutional identity verification and independent dossier review remain mandatory.
- No real institutional keys, Staging database, device/OIDC checks, SIEM receipts, signoffs or research ethics approval have been established in this change.
