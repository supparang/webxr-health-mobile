# ACTIVA-AI S2.3 — Security Logging and Monitoring

**Status:** DRAFT security proposal. **No Production data change or deployment.**
Applies to `server/security-monitor.js`, `server/index.js`, and CI tests.

## 1. Existing persistent record vs new telemetry

ACTIVA-AI already has a persistent `AuditLog` database model for important business operations, including actor/entity references and action metadata. **Do not replace this audit table.**

S2.3 adds **process-local, privacy-preserving observability** to detect short-term security anomalies and support incident triage. It must not be represented as a durable enterprise Security Information and Event Management (SIEM) system.

- HTTP 401 -> `AUTH_DENIED`, 403 -> `ACCESS_DENIED`, 429 -> `RATE_LIMITED`, 5xx -> `SERVER_ERROR`.
- Successful authenticated API requests -> **aggregate** `AUTHENTICATED_REQUEST`. This is **not** a true `LOGIN_SUCCESS` event: Google ID tokens are verified for each request and ACTIVA-AI has no backend login session boundary. Accurate interactive sign-in auditing needs a separately designed login/session event with consent and proper retention.
- Critical successful database audit operations -> `PERMISSION_CHANGE`, `ACCOUNT_CHANGE`, and `PRIVILEGED_ACTION` **after the AuditLog write has succeeded**. The existing database record preserves actor/entity detail for a proper authorized investigation.
- Each category is aggregated over a 15-minute fixed window. Thresholds: 25 authentication denials, 20 forbidden results, 20 rate-limit results, or 10 server failures during the window. An alert is logged **once per category per window**; the first 8 events per category/window are sampled to limit noisy provider logs.
- `GET /api/operations/security-summary` requires **ADMIN** and returns only current-process aggregated counters, threshold alerts, window start and time. It is not a historical security dashboard.

## 2. Privacy and log hygiene

Security events include an approved event category, timestamp, HTTP method, route **template**, response status, and validated request ID. Never include:
- names, employee IDs, email addresses, user IDs, personal/guest/study IDs;
- access/refresh tokens, OAuth JWTs, QR secrets, Guest Pass / Blind Review bearer tokens;
- client IP, full URL, raw path parameters, query strings, request/response bodies or evidence payloads.

The existing HTTP access logger previously emitted raw `req.path`, which can contain URL parameters. S2.3 substitutes a **server-defined route template** such as `/api/activities/:activityId` (or `UNMATCHED_API`), preventing accidental PII leaks. External reverse-proxy, CDN or web-server logs need their own independent body/query/path-redaction review.

Provider log retention baseline remains **30 days maximum**, subject to the approved incident-preservation exception described in `docs/v1.0.16-production-operations-policy.md`. GitHub workflow logs are subject to separate provider retention and permissions.

## 3. Escalation and response (not yet deployed)

Structured `security_alert` records go to process stdout/stderr. **They do not, by themselves, send a notification**. Before Production Security GO:
1. Configure the actual hosting provider's supported log sink/alert service to ingest `type=security_alert` from all production instances.
2. Configure an owned monitored notification route for the institutional incident responder, plus a fallback destination, and confirm a failure-to-deliver alert.
3. Test one synthetic threshold crossing in Staging; retain an alert-delivery and acknowledgment record, and then test recovery/closure.
4. Define severity, response owner, availability on evenings/weekends, log search access, and a retention/delete schedule.
5. If running more than one Node.js process, use centralized aggregation/alerts; the process-local counters are incomplete for the cluster.
6. Confirm data-protection officer/security/operations review before exposing any actor-identifying investigation data in a separate audited interface.

## 4. Verification and limitations

CI tests:
- `node tests/security-monitor.mjs` — category counts, bounded event sampling, once-per-window alert, redaction, stable route templates, timer boundary, action mirror.
- `tests/smoke.mjs` — ADMIN-only summary, denied Participant access, missing authentication, counters increment.
- Production API is **never** called by these tests.

**Known gaps:** no centralized historical event store; no log-integrity seal or WORM provider storage; no verified delivery of operator alerts; no distributed metric aggregation; no explicit interactive OIDC sign-in success/logout record. S2.2 rate-limit events are counted as 429 **when S2.2 code is integrated**; S2.3 does not merge PR #137 or make that limiter active on main.

**Acceptance remains HOLD** pending full CI, independent security review, staging alert routing/delivery test, log retention verification and written go/no-go review. PR #136 (least privilege), PR #137 (rate limiting) and this PR require controlled integration testing before any Production GO.
