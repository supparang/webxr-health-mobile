# P3.3 — Production Reliability & Operational Hardening

## Purpose and boundaries

Follow-up to Guest UI acceptance [#110](https://github.com/supparang/webxr-health-mobile/issues/110), the intermittent Production Monitor timeout incident [#111](https://github.com/supparang/webxr-health-mobile/issues/111), and the Dynamic QR UI fix [PR #112](https://github.com/supparang/webxr-health-mobile/pull/112).

Only software/monitoring and disposable-CI test fixtures are changed. No Production Prisma migration, Production data edit, role reassignment, OAuth bypass or direct participant identifier is permitted. A successful availability probe is **not** permission for autonomous decisions or empirical research export.

## Production cold-start policy

- Probe `/api/live` first, then `/api/ready`, then `/api/health`; avoid three simultaneous wake-up requests on sleeping Render Free instances.
- Each endpoint has up to **three bounded attempts**: 12, 25 and 65 seconds (plus 1.5 and 3.5 seconds of backoff). Maximum per endpoint is approximately 107 seconds; worst-case three-probe budget approximately 321 seconds, within the 8-minute workflow job ceiling.
- Retry transport timeout/network/abort and HTTP 408/429/502/503/504. **Do not** retry HTTP 200 with malformed JSON, HTTP 401/403/500, or any parsed 200 response that violates the established readiness/governance rules.
- Never treat a transient HTTP status or an exhausted retry sequence as success. All three final snapshots must still pass exact release/tier, database, Google OIDC/expected-domain, Production GO and `autonomousDecision === false` validation.
- The monitor emits only sanitized attempts (endpoint, attempt count, status, duration and reason): `HEALTHY_FIRST_ATTEMPT`, `TRANSIENT_RESPONSE_RECOVERED`, `TRANSIENT_PROBE_EXHAUSTED`, or `GOVERNANCE_OR_READINESS_FAILURE`. `TRANSIENT_RESPONSE_RECOVERED` suggests but does **not** diagnose a cold start.
- Incident routing is unchanged: verified failure creates/updates a GitHub incident, verified recovery comments and closes it. The safe classification is added to the audit text. Deliberate `simulate_failure` remains isolated from Production data.

## P4.5 strict deployed-source verification (read-only)

Render documents `RENDER_GIT_COMMIT` as the runtime SHA for a deployed revision. `/api/live`, `/api/ready` and `/api/health` expose only `sourceCommit`: a lowercase 40-hex git SHA or `null` if unavailable/invalid. This is non-sensitive revision metadata and contains no Render token or private configuration.

After the authorized operator deploys the approved Phase 4 commit on Render, open **Actions → ACTIVA-AI Production Monitor → Run workflow** and enter its **exact full 40-character deployed SHA** in `expected_source_commit` (leave `simulate_failure=false`). The read-only workflow requires all three endpoints to return that exact revision and existing liveness/readiness/GO/OIDC/human-decision guards to pass. A stale deploy, missing fingerprint or mixed revisions fails explicitly; blank `expected_source_commit` keeps recurring scheduled monitoring backward-compatible until manual verification. Do not pass a token, a credential, a branch name, a short SHA or a fictitious revision.

The GitHub `main` commit, deployed Render service revision, and optional GitHub Pages frontend revision may differ because service deployment can lag; log each independently. CI or `sourceCommit` alone cannot verify actual research ethics/site authorization, data provenance or participant consent. Keep the empirical-collection gate disabled until genuine human approval.

## Deployment / acceptance gates

1. PR changes limited to monitor verification, monitoring workflow, disposable CI fixtures/tests and this documentation; no Production secrets in logs.
2. ACTIVA-AI CI (push and PR) PASS: monitor retry regression, existing Guest E2E and QA export exclusion integration, QR DOM regression and production Docker smoke.
3. Merge to `main` only after CI PASS.
4. Confirm Render is Live on the resulting `main` commit, noting any automatic rebuild. For changes only to monitoring scripts and tests, the existing application runtime remains functionally unchanged.
5. A read-only **ACTIVA-AI Production Monitor** run is automatically triggered when monitoring code/workflow is merged to `main`; inspect strict liveness/readiness/governance PASS and its retry classification. The existing manual dispatch and six-hour schedule remain available. Repeat scheduled monitoring for a sleeping instance to assess cold-start behavior in practice.
6. Verify the old incident #111 remains resolved and a deliberate synthetic-failure alert, if used, is clearly marked as a routing test; do not claim true outage recovery from a simulation.
7. Record sanitized CI URLs, deployed commit, monitor run, export-isolation test log and any residual operational follow-ups in the P3.3 PR.
