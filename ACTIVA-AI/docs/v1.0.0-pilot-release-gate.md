# ACTIVA-AI V1.0.0 — Pilot-Ready Release Gate

## Release principle
V1.0 separates three decisions:
1. Evidence Engine result
2. Human participation decision
3. System pilot release decision

The AI layer cannot make either Human Final Decision or Production GO.

## Release gate
Endpoint:
`GET /api/operations/release-gate`

Roles:
- ADMIN
- STAFF

Response:
- releaseVersion
- gate: GO | HOLD
- blockers
- security readiness
- review-monitoring snapshot
- immutable activity closure snapshot
- backup/recovery state
- acceptance scenarios
- latest audited release decision

The endpoint is aggregate-only and declares `containsPII: false`.

## Immutable activity closure
Endpoint:
`POST /api/operations/activities/:activityId/close`

Role:
- ADMIN

Prerequisites:
- Activity ended
- Every non-void record has Evidence Evaluation
- No unresolved Human Review
- No critical Data Quality issue
- Closure reason >= 10 characters

On success the activity stores:
- pilotClosedAt
- pilotClosedById
- pilotClosureNote
- pilotClosureVersion
- pilotClosureHash
- pilotClosureSnapshot

The closure snapshot contains no direct participant name or employee ID. It captures record IDs, system evidence status, final evidence status and latest Human Review references.

### Operational mutation lock
After closure the server responds HTTP 423 `ACTIVITY_PILOT_CLOSED_IMMUTABLE` for:
- assignment changes
- participant-scope changes
- Dynamic QR issuance
- check-in
- check-out
- staff-assisted check-out
- staff verification
- attendance void
- Evidence re-evaluation
- Human Review

Research/ground-truth labeling remains separately governed and is not treated as an operational evidence mutation.

## Backup
Endpoint:
`GET /api/operations/backup`

Role:
- ADMIN

Backup:
- contains PII
- contains no signing secret
- intentionally excludes QrToken and PersonalQrCredential
- includes SHA-256 checksum
- includes collection counts

Security rationale:
after disaster recovery, ephemeral QR credentials should be reissued rather than silently reused.

## Recovery verification
Endpoint:
`POST /api/operations/recovery-check`

Role:
- ADMIN

Validates:
- format
- required collections
- collection counts
- checksum
- release-version match

It does not restore data and returns:
`destructiveRestorePerformed: false`

Successful checks are audited as:
`BACKUP_RECOVERY_CHECK_PASSED`

## GO / HOLD decision
Endpoint:
`POST /api/operations/release-decision`

Role:
- ADMIN

Reason >= 10 characters.

Audit actions:
- PILOT_RELEASE_GO
- PILOT_RELEASE_HOLD

GO is rejected when hard release blockers remain.

## Runtime acceptance scenarios
1. SECURITY_CONFIG
2. HUMAN_FINAL_DECISION
3. ACTIVITY_IMMUTABILITY
4. BACKLOG_TARGET
5. DATA_QUALITY
6. BACKUP_RECOVERY

These are system/process readiness controls, not personnel scores.

## Demo behavior
Demo Mode mirrors the workflow but:
- checksum uses demo-only FNV-style hashing
- synthetic data only
- Production GO is always blocked
- release gate is always HOLD

This prevents a browser demo from being confused with production approval.
