# ACTIVA-AI S2.2 — API Protection and Request Throttling

**Scope:** defensive throttling only; not a claim that external DDoS, distributed rate limits or penetration testing is complete.
**Change control:** PR is DRAFT, isolated from S2.1 authorization PR. No Production deployment or data mutation.

## Enforcement
- `NODE_ENV=production` enables application throttling automatically; `ACTIVA_RATE_LIMIT_ENABLED=false` on `PRODUCTION` is a configuration error. Non-production defaults OFF to preserve existing synthetic smoke fixtures; `ACTIVA_RATE_LIMIT_ENABLED=true` turns it on in staging.
- Three cumulative layers, all fixed 60-second windows:
  1. **General API/IP:** 3,000 requests/IP; excludes `/api/live`, `/api/ready` and `/api/health` so monitoring keeps working. Client IP is `req.ip`, which defaults to the direct socket peer (not untrusted `X-Forwarded-For`).
  2. **Public bearer APIs:** Guest 900 requests/IP + 36 requests/GuestPass, Blind Review 300 requests/IP + 36 requests/BlindReview pass. The pass key is a SHA-256 fingerprint, kept in temporary process memory only. Missing or malformed credentials remain limited by the IP layer.
  3. **Authenticated APIs:** 600 requests/actor and 180 state-changing requests/actor (POST, PUT, PATCH, DELETE), after successful authentication. Distinct logged-in users behind the same NAT have individual actor quotas.
- Exceeding a bucket: HTTP **429**, `RATE_LIMITED`, `Retry-After`, and `Cache-Control: no-store`; no token/IP/user ID in security rate-limit logs.
- Memory is bounded to 25,000 active bucket keys per limiter. A saturated store fails closed with **503** `RATE_LIMIT_CAPACITY_EXCEEDED` rather than evicting active counters. Counters are automatically cleaned on subsequent requests after their windows expire.
- Existing role authorization, QR cryptographic validation, consent and verification are **not** replaced by these limits.

## Operational limitations and risk

**Per-process only:** counts reset on restart and are independent per instance. Do not interpret this as cloud-wide attack mitigation or use it instead of CDN/WAF/edge quotas. Approve and deploy a shared distributed store/edge rate limiter if horizontal scaling is introduced. Consider a stronger identity-based backstop on unauthenticated malformed-token traffic for higher-risk environments.

**Trusted proxy:** `app.set("trust proxy")` is intentionally not enabled in this PR. A public-facing reverse proxy can cause all users to appear as one IP. Never trust arbitrary `X-Forwarded-For` sent by clients. Before enabling a trusted proxy, document and verify the *actual* reverse-proxy topology, allowed ingress path and express trusted-proxy configuration with security review. When in doubt retain default untrusted forwarding and use per-pass/per-actor keys for legitimate users. Verify that a forged `X-Forwarded-For` cannot evade throttling.

**Classroom concurrency:** thresholds are only conservative starting assumptions (a 200-participant event may share a NAT). Perform representative 200+ participant load tests of login, QR check-in/out, guest session and retries using synthetic data. A rate limit must not block normal check-in under approved peak load. Document real 429 metrics, thresholds, and rollback/HOLD criteria.

**Privacy:** operational `security_rate_limited` log events contain only category and request ID. Do not add bearer tokens, IPs, private IDs, or request bodies to this log. If security investigation needs IPs, use separately approved, time-bounded access records with appropriate governance rather than expanding application logs indiscriminately.

**Fixed-window trade-off:** boundary bursts of up to twice the quota can occur across two windows. Treat this as a first hardening layer. Distributed sliding windows/edge enforcement can be adopted after scaling assessment.

## Tests

- `node tests/rate-limit.mjs`: standalone in-process and localhost Express tests; no PostgreSQL; no Production endpoint; checks 429, Retry-After, counter expiry, bounded-memory 503, per-pass isolation on same IP, independent authenticated user buckets, monitoring bypass and fail-closed deployment settings.
- `.github/workflows/activa-ai-ci.yml` adds standalone S2.2 test before legacy smoke suite.
- Require **full ACTIVA-AI CI PASS**, staging acceptance with traffic replay and operator review before merging.

## Release decision

**HOLD:** while there is no successful CI, no validated actual-proxy/source-IP behavior, no load test at expected participant concurrency, or no operator approval.
**GO:** only after end-to-end QA and security governance sign-off for the specific deployment architecture.

S2.1 permissions and Phase 4 research ethics gates are independent of this PR; S2.2 passing does **not** authorize Production or human-subject research.
