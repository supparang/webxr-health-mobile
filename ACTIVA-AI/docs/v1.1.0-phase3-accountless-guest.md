# ACTIVA-AI Phase 3 P3.2.3 — Accountless Guest Participation

**Status:** Software implementation; empirical study recruitment and human ethics approval remain separate decisions.

## Why

Real participants need not hold Google/ACTIVA-AI accounts. A Guest Participant is a separate database entity, NOT a dummy `User`. Attendance has exactly one owner: existing `User` OR `GuestParticipant` (database CHECK constraint). No guest name, email, employee number, phone or direct identity is collected by the Guest Pass flow.

## Enrolment and scientific participant linkage

1. ADMIN prospectively creates an activity with `dataClassification=EMPIRICAL` and approved research governance, or `QA_TEST` for software acceptance. `UNCLASSIFIED` cannot issue guest passes.
2. Activity participation mode must be OPEN and its checkout window still open.
3. ADMIN obtains a pseudonymous *offline* code of the form `SUBJ-[A-Z0-9_-]{6,64}`. **Never enter personal identifiers as a study code**. For repeat attendance by the same real person across activities, reuse the same offline study code, maintaining the separately protected identity mapping under the research protocol.
4. Server calculates an HMAC-SHA256 of the study code using the configured `RESEARCH_HASH_SALT`. Plain study code is neither persisted nor included in audit, and the guest pass is not a persistent system account.
5. ADMIN supplies protocol-approved consent statement (30–4000 characters) and explicit version. The application does not determine ethics approval of this text. ADMIN attests that the enrolled participant is real and that the study code is pseudonymous.
6. A distinct cryptographically random 32-byte URL-fragment Guest Pass is returned **once**; database stores only SHA-256 token hash. Link must be delivered privately. An on-screen pass QR is generated in ADMIN UI. The pass is scoped to one activity and expires shortly after its checkout window.

## Guest mobile flow

- Open `/guest#token=...` — fragment is removed from the address/history immediately and subsequently submitted exclusively as `Authorization: GuestPass <token>` with no cookies.
- Read actual approved consent text and voluntarily accept its exact version. Before consent, check-in is rejected.
- Scan fresh, organizer-issued CHECKIN Dynamic QR on site. Browser native `BarcodeDetector`/camera supported where available; manual token entry is an accessible fallback. Server independently validates HMAC signature, event ID, purpose, expiry **and** active stored QR hash/nonce.
- Initial guest `identityVerified=false`: pass possession is **not** proof of identity. An assigned STAFF or ADMIN must witness the person in place, confirm matching privately held study registry/Guest Ref and explicitly submit `guestIdentityWitnessed=true` via existing Staff Verification. The resulting identity and staff evidence changes are audited.
- Same Guest Pass and fresh CHECKOUT Dynamic QR must be used during the checkout window. Double check-in and double checkout reject through the database unique/atomic guards.
- Participants can withdraw consent from the Guest Page. ADMIN can document withdrawal on their behalf if they lost access. The pass is revoked and research queries exclude records, while the operational immutable Ground Truth/Audit are retained.

## Research and isolation

Research `EMPIRICAL_ATTENDANCE_FILTER` excludes QA_TEST, UNCLASSIFIED, voided, guest records without consent, withdrawn or revoked passes.

Guest participant hashes are stable across activities **only if the same offline study code is reused**. This is required for planning unique-participant counts and prospective group separation. Server never passes NULL `userId` to research hashing: guest uses domain-separated `GUEST|<HMAC study hash>`; logged-in User behavior is unchanged.

The Guest Pass itself does **not** establish research sufficiency. Two different human blinded reviewers, Ground Truth locking, approved prospective sample plan, and final-test firewall remain mandatory before empirical training. Any QA guest activity remains excluded even when it has LOCKED Ground Truth.

## Operational safeguards

- 32-byte CSPRNG bearer token; token hash only persisted.
- Exactly one guest attendance for one Guest Pass; DB constraint prevents replay/concurrent duplicate creation.
- No direct participant PII in public guest session/response.
- Guest access checks revoked/withdrawn/expired state and only exposes its enrolled activity/own attendance.
- Endpoint authorization is independent of Google; all ADMIN issuance/list/revocation/withdrawal uses the existing authenticated ADMIN middleware.
- ADMIN only receives raw link once. A compromised pass can be revoked. An unused revoked pass can be reissued with renewed consent; passes with attendance or final withdrawal cannot be reissued.
- Public access logs store path/status/duration, not Authorization/token/body.
- Operational backup retains pseudonymous guest metadata but deliberately excludes `GuestParticipant.passTokenHash` and all ephemeral QR credentials. Protect backup access since it contains other operational data.

### Limitations

The guest flow is bearer-based, not individual biometric identity proof. Human witness attestation can be independently audited but must be implemented in the field according to the approved study protocol. Browser camera QR scanning requires supported `BarcodeDetector`; manual signed QR token is the documented fallback. Downloaded historical research extracts cannot be automatically recalled after a withdrawal: operator must invalidate affected extracts and rebuild any downstream models/reports.
