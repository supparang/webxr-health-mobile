# ACTIVA-AI S2.14 — Security Reviewer Findings & Delivery Hardening

**Technical review result:** TWO confirmed gaps in the S2.4 GitHub alert
adapter have been addressed in this Draft PR. The review is a source-level
audit and synthetic regression check, **not** an independent accredited
security assessment or real Staging acceptance.

## Findings

| ID | Severity | Evidence in prior code | Mitigation |
| --- | --- | --- | --- |
| SEC-S214-01 | MEDIUM — duplicate or fragmented incident reporting | `createSecurityAlertDispatcher().enqueue()` previously invoked `deliver()` concurrently for the same incident category. Two overlapping 15-minute windows could both read `GET /issues` before either `POST /issues`, causing multiple issue creations. | Use an **in-process per-category serial promise tail** so each active category completes its prior GitHub request before re-checking/creating/commenting. A queued alert remains a distinct notification. |
| SEC-S214-02 | MEDIUM — false-positive incident delivery acceptance | The adapter accepted any successful `2xx` JSON response on `POST /issues` or `POST /issues/:n/comments`, even `{}` or `{number:0}`, and incremented `delivered`. | Require GitHub to return a **positive safe-integer Issue `number` or comment `id`** before incrementing delivery success. On malformed response, record a generic, private-data-free FAILED event instead. |

The regression test `tests/security-alert-concurrency.mjs` exercises:
- Two alerts for the same category delivered concurrently; exactly one
  Issue creation followed by a comment, not two Issue creations.
- Strict rejection of missing/zero/string issue numbers and missing/null/
  non-integer comment IDs.
- Ordered queued alerts after the previous request failed.
- No raw token, IP, participant ID or bearer credential in Issue content
  and structured delivery-status logs.
- Alert delivery DISABLED by default and no outbound request in this mode.

These checks run alongside all previous S2.1–S2.13 automated tests and
the original S2.4 dispatcher tests. No real GitHub Issue was created.

## Residual operational blockers

**Single-process limitation remains:** this mitigation serializes requests
inside one Node process. Multiple replicas or simultaneous restarts may
still race to create GitHub Issues. An enterprise-grade central queue
and GitHub/API idempotency process needs a reviewed architecture.

**GitHub 2xx is not human acknowledgment.** A receipt means that the
remote API has accepted the update; it does not mean a designated operator
has been notified, read, acknowledged or acted on it.

**No durable queue:** an outage, process crash, excessive concurrency or
failed GitHub response may lose an external alert. Protected provider/SIEM
logs remain the record of security anomalies. Staging must test a
fallback channel before Production authorization.

**Independent security signoff still missing:** this internal corrective
pass is not a substitute for third-party/source code review of all Diff,
access-control policy, token handling, application load behavior,
institutional data minimization and actual Staging on approved infrastructure.
